## Background

`pr-workflow` は単一タスクを深く回す。`issue-fleet` は複数 issue を浅く広く回す（サブエージェント、
draft PR 止まり、trivial〜small）。**「深く × 広く」の象限が空いている**。

実運用で、assign 済みの複数 issue を独立した CLI セッションとして tmux で並列起動し、各セッションに
`pr-workflow` を全長（GATE 1 → CI → multi-review → review-resolve-loop → GATE 3）走らせ、停止のたびに
オーケストレーターが検証して代理応答し、GATE 3 だけを user へ上げる、という運用を実践した。

この運用は再現価値があるが、**同じ失敗を再発見するコストが高い**。実際に踏んだ失敗:

- スピナー文字列での停止検知が、稼働中のセッションを「停止」と誤判定した（差分方式へ作り直した）
- 状態を確認しない一斉配信の Enter が、開いていた選択肢を無言で選び、**誰も答えていないのに
  「ユーザー承認済み」と PR 本文に記録された**
- 長文送信の直後の Enter が取りこぼされ、指示が未送信のまま滞留した
- セッションの自己診断が誤っていた事例が複数あった（CI 失敗を「既存 flaky」と誤診断、
  「base ブランチ側の既存違反が原因」と誤診断、「本 PR と接点なし」と誤判断）。いずれも
  そのまま承認していれば実在する回帰を見逃していた
- 別運用では、重複投入された古いセッションが **merge gate を経ずに無断マージ**した事故もある

## User Story

複数の assign 済み issue を抱える開発者として、依存関係とコンフリクトを踏まえた波に割り、独立セッション
として並列に走らせ、停止のたびの判断を安全な範囲で委任し、**マージ判断だけを自分の手元に残したい**。

## Acceptance Criteria

- **AC-001** Phase 1（棚卸し → issue 依存グラフ → 同一ファイル衝突分析 → wave 割り → 起動コマンド生成）が
  tmux 不在でも完了し、そのまま貼れるコマンド列を返す。
- **AC-002** Phase 2 以降（起動・監視・代理応答・後始末）は tmux を前提とし、不在なら Phase 1 の成果物を
  返して停止する。
- **AC-003** 停止検知は、間隔を空けた 2 回のペインキャプチャの差分で稼働／停止を判定する。スピナー文字列の
  照合に依存しない。バックグラウンドシェル待ちは停止として扱わない。
- **AC-004** 監視開始時に検知器の自己診断を行い、既知の状態を判別できなければ**黙って進まず中止**する。
- **AC-005** セッションへの送信は次の性質を満たす。(a) 状態を分類していないペインへ送らない、
  (b) 意図しない選択肢が選ばれない、(c) 送信が成立したことを検証してから次へ進む、
  (d) 自由記述の指示が選択肢の回答として解釈されない。
- **AC-006** 代理応答は問いの種別で自動判定する。ただし次の 3 点で受け止める。
  (a) 無条件エスカレート集合（マージ / 履歴書き換え / 外向き不可逆操作）は分類器が上書きできない、
  (b) 判断に迷えばエスカレートする（fail-closed）、
  (c) **事実主張に依存する問いは、一次ソース検証を通してからでないと自動応答しない。**
- **AC-007** 子セッションの model / effort は `model-fitness-check` の contract を参照して選ぶ。
  contract テーブルを再掲しない。floor を下回る model で起動する場合は user の明示承認を得てから
  事前承認ブロックをプロンプトへ前置する。
- **AC-008** quota を起動前と各 wave 境界で読み、並列度と model 選定へ反映する。読むのは**親と同じ
  profile のプール**（profile ごとに独立しており、同時刻に別の値を取る）。閾値超過時は黙って進まず
  選択肢を提示して停止する。
- **AC-009** 起動前に同名セッションの存在を確認し、重複起動しない。
- **AC-010** 共有リポジトリへの git 操作（既定ブランチの最新化等）は子セッションに行わせず、
  オーケストレーターが直列に 1 回だけ実行する。
- **AC-011** 環境から復元できない決定事項（wave 計画と根拠 / 委任境界 / quota 方針 / 訂正履歴）だけを
  state file に持つ。セッションの生死・PR・CI・ワークツリーは毎回 tmux と `gh` から再取得し、
  キャッシュしない。
- **AC-012** セッション終了は user 承認を得たうえで、プロセスの身元確認後に行う。
- **AC-013** 子セッションの launcher は親の `CLAUDE_CONFIG_DIR` の basename から導出し、親と同じ profile で
  起動する。明示指定があればそれを優先するが、**親と異なる profile で起動する場合は user の明示承認を
  必須**とする。quota が逼迫していても、自動で別 profile へ負荷を逃がさない。
- **AC-014** 子には orchestrator 用の model variant を使わない。子は `pr-workflow` の実行者であって
  オーケストレーターではなく、orchestrator prompt が不要なうえ model floor の判定も変わる。

## Considered Alternatives / Rejection Rationale

| 検討した案 | 却下理由 |
|---|---|
| `issue-fleet` に deep モードとして統合 | サブエージェント方式と独立セッション方式という 2 つの実行モデルを 1 skill が抱える。`issue-fleet` 自身の「浅く広くが領分」という定義とも矛盾する |
| 「計画・起動」と「監視・代理応答」を 2 skill に分割 | 起動直後に必ず 2 つ目を呼ぶ手間が常に発生する |
| 代理応答を既定 ON | 明示委任なしに gate や設計判断が承認される。→ 種別による自動判定 + 3 点バックストップを採用（AC-006） |
| 代理応答を明示委任のみ（opt-in） | user 判断で不採用。種別判定 + バックストップで代替する |
| 分類器のみ（バックストップなし） | 実運用で複数の誤診断を差し戻している。いずれも「可逆で内向きな選択肢」であり、可逆性の軸だけでは捕まらない |
| 一次ソース検証を努力目標に留める | 同上。危険は操作の可逆性ではなく、問いが乗っている事実主張の正しさにある |
| 選択キーを一切使わず常に自由記述で指示する | 誤選択は構造的に防げるが、単純な承認でも毎回再推論させることになる。事故の真因は選択キーではなく、分類なしの一斉配信だった |
| tmux 必須（不在なら skill 中止） | 計画とコマンド生成だけでも実際に価値が出ていた。フェーズで切れば両立する |
| 検知手順を文章で記述し毎回実装させる | 差分方式・バックグラウンド待ちの分岐・入力欄判定は作り直しを重ねた知見。毎回踏ませる理由がない |
| 新 skill が tier → model 対応表を持つ | `model-fitness-check` が SSOT を宣言し再掲を明示的に禁止している（drift 再演の防止） |
| quota を扱わない | 実運用で quota は計画を複数回変えた。読み先と閾値は `model-fitness-check` に既存 |
| 全状態を state file に保存 | 実態とずれたときに気づけない。生の状態は環境が真実を持つ |
| 全フェーズを評価対象にする | 実セッション起動・実リポジトリ変更・マージを伴う。ハーネス構築コストが skill 本体を上回る |
| quota の空いている profile へ自動で振り分ける | quota は profile ごとに独立プールなので構造的に可能だが、**業務を別区分のアカウントで走らせ得る**。`model-fitness-check` も profile 間でセッション状態が分離している旨を警告済み。スループットと引き換えにしてよい性質ではない |
| launcher を毎回 user に尋ねる | ほぼ常に「親と同じ」が答えになる問いを毎回出すことになる。継承を既定にし、逸脱時のみ承認を取る形で足りる |
| 子も orchestrator variant で起動する | 子は実行者であり orchestrator prompt が不要。当該 variant は model floor を全て pass するため floor 判定が実質無効化される |

## Out of Scope

- 横断リポジトリの収集と優先度付け → `repo-radar` の領分（本 skill はその出力を入力に取れる）
- trivial〜small の浅い並列処理 → `issue-fleet`
- 単一タスクの深い orchestration → `pr-workflow`
- レビューのバッチ適用 → `review-fleet`
- Phase 2 以降の自動評価ハーネス
- **マージの代理実行**（無条件エスカレート集合の筆頭）
- Phase 2 以降の harness 非依存化。launcher が Claude Code 固有であるため、Phase 2 以降は
  Claude Code 前提とする（Phase 1 は harness 非依存を維持する）

## Open Questions

- 並列度の既定値。`issue-fleet` は 4、実運用では 7 で走らせて週次 quota の閾値帯に入った。
  quota 従属にするとして初期既定をいくつに置くか
- レビュー roster の絞り込み指示は、実運用では実効がほぼ無かった（`multi-review` が設計上すでに
  別 harness 偏重で、Claude 側の leg が元から最小だったため）。効くレバー／効かないレバーの実測表を
  本 skill に書くか、`multi-review` 側へ寄せるか
