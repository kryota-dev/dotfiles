# model-update

更新されたモデルを調査し、手元の構成のどこに関わるかを整理する。ユーザーの判断を得て、反映を pr-workflow に渡す。
この skill は定義ファイルを編集しない。反映の手順（worktree・実装・CI・レビュー）を二重に持たないため。
モデルの値と性質の正本は [model-roles.md](../pr-workflow/references/model-roles.md) と定義ファイル。

## 止まるところ

ユーザーの判断で止まるのは、次の 3 つである。

1. Phase 4 の判断（上げる・据え置く・A/B で確かめる）。
2. モデルの差し替えを超えて、役割の構成（段の数・系統の分担）を変える案を出すとき（確定済みの決定のため）。PRD に書かれたモデルの値は当時の値なので、同じ段の中の差し替えは、構成の変更に当たらない。
3. pr-workflow に渡した後は、pr-workflow の承認点に従う。

公開の事実を確かめられなかったときは、確かめたことを報告して終える。

## Phase 0: 対象の特定

- 依頼からモデル名と提供元を取る。無ければ、いま構成が使っている提供元（Phase 2 の `git grep` で調べる）について、新しいモデルが出ているかを調べる。
- 旧モデルは、提供元の移行のガイドの移行元と、手元の構成にある同じ系列の ID から決める（依頼には、新しいモデルの名前しか無いことが多いため）。
- 棚卸しと反映の対象は dotfiles のリポジトリである。別のリポジトリのセッションなら、調査まで進めて、棚卸しから先は dotfiles のセッションで頼むよう伝える。
- スクラッチに作業用のディレクトリ（例: `<scratch>/model-update/<対象>/`）を作り、調査のメモ・比較の HTML・A/B の結果を置く。

## Phase 1: 調査

先に [sources.md](references/sources.md) を読む。

1. **公開の事実を先に確かめる。** 公開前の「まだ出ていない」という記事や予告が混ざるため、記事の日付と今日の日付で新旧を判定し、古いものは捨てる。提供元の一次ソースで公開を確かめられなければ、構成を変えず、確かめたことを報告して終える。
2. **一次ソースを読む。** 種類は sources.md の表に従う。403 などで読めなかったページは「読めなかった」と書き、ほかの記事から孫引きした数値にはその旨を付ける。「このモデル専用のガイドは無い」も結果として書く。
3. **ハーネスの側を読む。** モデルが使える CLI の版、プランごとの提供、既定の変化を調べる。
4. **第三者の評価と利用者の声を読む。** 自己申告（提供元の表）と第三者の測定を分け、食い違う数値は並べる。公開から何日分の評判かも書く。
5. **手元のハーネスで新しい ID を 1 回動かす。** sources.md の「新しい ID の試走」に従う。動かなければ原因を切り分けて比較に書き、「上げる」は推奨しない。
6. 出典の URL と読んだ日を付け、結果を作業用のディレクトリのメモに残す。

取得した内容を別の役割に渡すときの囲み方は、model-roles.md の「弱点への対策」に従う。

## Phase 2: 棚卸し

`git grep -n` でモデルの ID と名前を全部拾う。
検索語は、対象の系列がいま使っている ID のすべて、表示名（空白を含む表記）、系列の名前、同じモデルの別の名前、新しい ID。
新しい ID が既に入っている箇所は、反映したときの根拠を新しい出典で照らし直し、「維持する・戻す」の判断の対象にする。
次のパスは書いた時点の例で、grep の結果を正とする。

| 種類 | 書いた時点の例 | 一緒に変わるもの |
|---|---|---|
| 役割の定義 | `home/dot_agents/roles/*.md`（Claude）、`home/dot_codex/agents/*.toml`（GPT） | 役割表、テスト |
| 役割表・割り当ての根拠・弱点への対策 | model-roles.md | 定義、テスト |
| ハーネスの既定 | Claude Code の `home/dot_claude/settings.json`、Codex の `home/dot_codex/modify_private_*.toml`、T3 Code の `home/private_dot_t3/private_userdata/modify_settings.json` | テスト、構成の文書 |
| テスト | `tests/`（役割・テンプレート・settings の検査） | — |
| 構成の文書 | `ARCHITECTURE.md` | — |
| 確定済みの決定の記録（PRD など） | — | 変えない（当時の値として残す） |

系統ごとに見落としやすい箇所も確かめる。

- Claude: Claude Code の既定と advisor のモデル、T3 Code の既定、Claude の役割の定義、model-roles.md の fallback 先のモデル、`ARCHITECTURE.md` の「settings から外した指定と理由」（旧モデルの性質を前提にした文）。
- GPT: Codex の既定と profile（モデルと effort）、GPT の役割の定義、`ARCHITECTURE.md` の T3 Code が Codex に送る effort の記述（特定の ID に結び付いている）。
- そのほかの提供元: 手元のハーネスから呼ぶ経路があるかを先に確かめる。無ければ、構成に入れる箇所は無い。

`gh pr list --state open` と `gh pr view <番号> --json files` で、同じファイルを触る進行中の PR を確かめる。あれば比較に書く（反映のときに衝突を避けるため）。
同じ更新を扱う自分の PR が既にあれば、その PR を土台にするかを Phase 4 の最初に聞く。

## Phase 3: 影響の整理

- **変えないものと理由を先に書く。**
- **影響を受ける箇所を証拠の強さで分ける。** 別々に判断できるようにするため。格上げ先だけのモデルと、多くの役割が使う主力のモデルは、外れたときの影響が違うので分ける。
- **旧モデルの廃止予定を確かめる。** 予定が無ければ据え置きも正当な選択肢になる。予定があれば期日を書く。
- **根拠の文は ID の書き換えで済ませない。** 旧モデルの評価を引く文は、新モデルの出典で書き直すか、据え置きの理由を書く。どちらにするかを「一緒に直すもの」に挙げる。
- **「最新モデル」を指す URL を旧モデルの出典として残すなら、読んだ時期を添える。** 中身が新モデル向けに替わるため。
- **effort を見直しの候補に入れ、公式の推奨を読む。** 段の名前が同じでも、考える量はモデルごとに違うため。推奨が出典の間で食い違えば並べて書き、役割が実際に動くハーネスの文書を優先する。
- **ID に結び付いたハーネスの挙動は、確かめられなければ「未確認のこと」に載せる。** 特定の ID にだけ送られる設定や、ハーネスのカタログに新しい ID があるかは、推測で書くと反映の後に外れるため。
- **対象が、この見直しをしているセッション自身のモデルや advisor なら、比較にその旨を書く。** 自分の系統の評価は第三者の測定と A/B に重みを置き、提供元の自己申告だけで「上げる」を推奨しない。ハーネスの既定を変えても、効くのは次のセッションからである。

比較を、外部の読み込みに頼らない 1 枚の自己完結した HTML として作業用のディレクトリに書く。
Artifact の道具があるハーネスでは、HTML を書く前にその道具の決まりを読み、それに合わせて書く（ページの外枠・題名・配色・外部の読み込みに条件があり、後から合わせると書き直しになるため）。
見出しは次の順にする。

1. 変えないもの
2. 影響を受けるもの（表: 箇所・今の値・状況）
3. 評価が割れている点（上がった・下がった・急ぐ理由の有無）
4. 一緒に直すもの（上げる場合と、据え置く場合。役割の本文は、新モデルの公式のプロンプトのガイドに該当箇所があるかも）
5. 確かめたこと・未確認のこと
6. 判断が要る点（Phase 4 の質問と同じ並び）

数値と主張に出典のリンクと読んだ日を付け、自己申告と第三者の測定を見分けられるようにする。
書いたら、Artifact の道具があるハーネスでは公開する。無ければ HTML のファイルのまま示す。
影響する箇所が無ければ、Phase 4 と Phase 5 を飛ばして、Phase 6 の記録へ進む。

## Phase 4: 判断

比較をユーザーに示し、次を聞く。

- 証拠の強さで分けたまとまりごとに 1 問にする。選択肢は「上げる」「据え置く」、評価が割れているときは「A/B で確かめる」。新しい ID が既に入っている箇所は「維持する」「戻す」にする。役割として起動できない箇所（advisor など）には「A/B で確かめる」を入れない（ab.md の手順で比べられないため）。判断の材料は、一緒に直すもの・費用・外れたときの影響である。
- 役割の構成そのものを変える案は、モデルの差し替えとは別の問いにする（確定済みの決定を変えるため）。
- ほかの問いの答えで要否が決まる問いは、その答えを得てから聞く。
- 「A/B で確かめる」が選ばれたら Phase 5 へ進む。結果を比較に足して公開し直し、同じ問いをもう一度聞く。

## Phase 5: A/B

評価が割れていて、ユーザーが選んだときだけ行う。先に [ab.md](references/ab.md) を読む。
役割を普段起動する形（effort と本文）はそのままにし、モデルだけを替えて同じ入力を渡す。
起動形は [codex skill](../codex/SKILL.md) と model-roles.md に従う。

## Phase 6: 反映と記録

変えるものがあれば、次の一覧を渡して [pr-workflow](../pr-workflow/SKILL.md) を起動し、1 つの PR にする。

- 変える箇所と新しい値。
- 一緒に直すもの（根拠の文・弱点への対策・テスト・構成の文書）。model-roles.md の「割り当ての根拠」の時点（何年何月時点の資料か）も含める。
- 変えないものと理由、未確認の点、出典と読んだ日。

[vault skill](../vault/SKILL.md) に従い、決めたこと・検討した代替案（据え置きを含む）・理由・A/B の要旨・未確認の点・次に見直すきっかけ（廃止予定が出たら、など）を記録する。
全部が据え置きでも記録する（次の回に同じ調査を繰り返さないため）。
