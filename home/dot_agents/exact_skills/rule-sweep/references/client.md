# クライアントモード

所属先の vault の教訓を一般化し、検査できた提案だけを personal の inbox に届ける。
personal の中身は読まない。状態と移動の記録は所属先の vault に置く。

## 1. 所属先と読む版を固定する（S2・S3）

[vault の skill](../../vault/SKILL.md) の解決を使う。personal に当たるときは [personal モード](personal.md) へ進む。
クライアントと解決できた後は、その vault 以外を検索・閲覧しない。
personal のパスは追記先としてだけ使う。モードの解決に必要な owner の確認以外は personal の内容を読まない。

実行の日時とクライアントの vault の `HEAD`（`pinned`）を記録する。
`notes/rule-sweep-moved.md`、`notes/rule-proposals.md`、作業ログ、出典、フロントマターは `git -C <vault> show <pinned>:<path>` で読む。
未 commit の追記は次回に回す。
移動記録の前回の基点以降に変わった提案とログを対象にする。
移動記録に残る「移す予定」の件も、変更の期間にかかわらず再試行の対象にする。
記録や基点が無い、履歴に無い場合は、未移動の提案全体と直近 14 日のログを読む。
この vault の外の出典を辿らない。

## 2. 移す前に出典を確かめる（S3）

所属先の `notes/rule-proposals.md` と作業ログの本人の指摘やエージェントの学びから、案件に依存しない振る舞いの提案を選ぶ。
inbox の項目の形と `source` の意味は vault の skill に従う。
`source: external`、由来不明、出典が `pinned` に存在しない件は移さない。
判定は元の文と元の vault で行う。personal へ届けてから判断させると、出典を読むために隔離を越えることになる。
`source` は元の値を保ち、外部由来を `agent` や `owner` に変えない。
`repo:`・`steward` が反映先の件は状態を変えず、件数だけを記録する。

## 3. 一般化して 1 件ずつ検査する（S1・S4・S8）

一般化と固有名を除く手順は、vault の skill の「知見の共有」を使う。
クライアント名・製品名・リポジトリ名・人名・URL・資格情報とそのメタデータを持ち出さない。
提案・理由・見出し・反映先をすべて確認する。
personal へ渡す出典は `client:<匿名のラベル>` と件の ID だけにし、元のノートのパス・commit は所属先の記録だけに残す。

ID は `rp-YYYYMMDD-<4 桁の 16 進>` とする。
日付は元の件の日付を使い、短いハッシュは元のノートのパスと、その件を最初に移す際の固定した commit から作る。
ハッシュの対応は移動記録に残し、再試行では同じ ID を使う。衝突があれば、別の件と区別できる ID を選んで対応を保存する。
本文を変えて別の件として出し直す前に、既存の移動記録と同じ趣旨でないか確認する。

1 件分の追記全文を vault の外の一時ファイルに置く。再試行では、移動記録に保存した全文をそのまま使い、書き直さない。
前検査と gitleaks での秘密情報の検査は、[personal モードの「公開前に検査する」](personal.md#6-文を整え公開前に検査するs1) に従う。

前検査を通り、終了コードが 0 の件だけ追記できる。検出、コマンド・設定の不足、実行失敗なら personal へ書かず、
その件を所属先に残し、状況のノートに理由を記録して止まる。
検出内容を personal や出力に転記しない。一時ファイルは処理後に `rm` で消す（`rm -rf` は Claude Code の deny に当たる）。

## 4. 移す予定を保存してから追記する（S6・S8・S9）

追記する前に `notes/rule-sweep-moved.md` に「移す予定」を書き、commit・push する。
1 件ごとに ID・元のノートのパス・元の commit・元の source・判定の結果・移動の状態と、検査を通した追記の全文を記録する。
再試行では「移す予定」の全文をそのまま一時ファイルへ戻して再検査し、同じ ID の本文を書き直さない。
commit と手入力の保全は vault の skill、push 前の fetch と祖先の確認は
[personal モードの「vault を先に保存する」](personal.md#5-vault-を先に保存するs6s7s9) に従う。
これは所属先と personal のどちらの push にも適用する。

予定の保存が成功したら、検査を通った一時ファイルの内容を、vault の skill の `>>` の手順で
personal の `_inbox/rule-proposals.md` に追記する。編集ツールで開かず、personal の既存本文・差分も読まない。
追記する件は ID・日付・author・target・source・提案・理由・匿名の出典・空の状態を持つ形にする。
personal の inbox を新規作成する場合も同じ追記方法を使う。存在の確認だけで本文を読まない。

personal の commit と push も vault の skill に従い、対象ファイルだけを commit する。
メッセージは `agent(<claude|codex>): rule-sweep client <ID>` とする。
personal モードがこの接頭辞で検査済みの移動を確認するので、省略しない。
認証・署名・push に失敗したら迂回せず止まり、「移した」にしない。

## 5. 移した記録を残す

personal の push が成功した件だけ、所属先の移動記録を「移した」に変え、commit・push する。
失敗した件は「移す予定」のまま残す。再実行では保存した ID と追記の全文をそのまま再使用する。
push 成功後に記録できず重複して届いても、personal モードが ID で 1 件にまとめる。
personal の内容を読んで重複を確かめようとしない。

今回の範囲の走査と記録の保存・push が成功したときだけ、移動記録の基点を入力の `pinned` に進める。
各実行で `notes/rule-sweep-status.md` に日時・固定した commit・検査済み ID・移した ID・対象外の件数・停止理由を残す。
0 件でも記録し、vault の skill の書式で commit・push する。
保存もできなければ、出力に理由と完了した操作を残す。personal の状況のノートは読み書きしない。
