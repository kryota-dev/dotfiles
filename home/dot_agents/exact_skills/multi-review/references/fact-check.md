# multi-review: 統合時の裏取り

reviewer の断定的な主張は、投稿する前に親が一次ソースで確かめる。reviewer は差分中心の限られた文脈で動くので、裁定は親に集める。

## 委譲

確かめる指摘が多ければ、1 件ずつ `fact-checker` に並列で調べさせてよい（どちらのハーネスからも model-roles.md の `claude_leg` で起動する）。`fact-checker` は WebFetch と WebSearch しか持たない。未検証の web の内容を読む leg に、ローカルのファイルを読む道具と外へ出す道具を同時に持たせないため、リポジトリとの照合は親が行う。subagent には「該当する記述の有無・引用・URL」を返させ、採否は親が引用と URL を読んで決める。

## 確かめる対象と手段

**技術的な主張**（「X は Y をサポートしていない」「Z は非推奨」など）:

1. 公式ドキュメントの現行版を引く（context7 など）。
2. 実装の実体を見る（`node_modules` の型定義や export など）。ドキュメントに無いことと実装に無いことは別の問題である。
3. コメントに URL を書くなら、そのページに該当する記述が実際にあるかを確かめる。

**「無いこと」を根拠にする指摘**（「保持期間が未定義」「ADR が無い」など）: PR 本文とリンク先の文書を読み、キーワードを探す。見つかれば誤指摘として捨て、見つからなければ「リンクされた文書を確認したが該当記述なし」と根拠を添えて採る。

## 反映

| 結果 | 反映 |
|---|---|
| 誤り | 統合サマリーから削除し、「事実検証で棄却した指摘」に理由と根拠を残す |
| 部分的に正しい | 訂正版に書き換え、根拠を添える |
| 裏が取れた | そのまま採り、根拠を添える |
| 確かめられない | 「（未確認の可能性あり）」と明示して残すか、投稿候補から外す |

候補の原文は実行記録に保持し、候補 ID ごとに重複判定と事実検証の採否を分けて記録する。指摘にしなかった疑いは各 leg の確認根拠に、親が候補を棄却した理由は統合サマリーに残す。前のラウンドの棄却台帳は親の判断材料にとどめ、leg に再提起を禁じない。
