# pr-workflow: turn を跨いで待たない（根拠）

**これは根拠である。** 規範（守ること）は `SKILL.md`「turn を跨いで待たない（実行モデル契約）」節が
持つ。ここにあるのは、その規範がなぜその形なのか —— 実測、事故の経緯、採らなかった選択肢とその理由。

平常運転では読まなくてよい。規範を疑ったとき・書き換えるとき・規範が想定していない待機に出たときに読む。

## 何が起きたか（#585・2026-09-01 実測）

`wave-orchestrator` が `fh session launch` で 4 本の子を並列起動し、各々に `pr-workflow` を全長
（gate → CI → レビュー → 指摘対応）走らせた。結果:

| 本数 | 結末 |
|---|---|
| 3 本 | 「CI の監視はバックグラウンドで進行中です。完了通知が来次第、Phase 6（`/multi-review`）へ進めます」と述べて turn を終えた。**PR は立ったがレビュー 0 件** |
| 1 本 | 背景タスクの待機上限に達して打ち切られ、**コミット 0 本**で終わった（作業結果が丸ごと失われた） |

`fh session launch` は `claude -p` の **1 turn 実行**である。turn を終えた子に次の turn は無いので、
待っていた通知は永久に来ない。

**記録上は完走と区別が付かなかった。** 3 本とも `fh runs` は `succeeded` / `exitCode: 0`、`denials` も
空だった（子は拒否されたのではなく、単に「やらなかった」ため）。気づけたのは PR のコメント数という
外形からで、harness の記録からではない。`adapter-claude` の結果解釈が見るのは「最後の result イベントの
`is_error`」と「プロセスの終了コード」だけで、子が何をしたかは見ていない（#573）。

**単一箇所の不具合ではない。** `pr-workflow` は orchestrator として複数の skill へ委譲し、その結果を
**次の turn で受け取る**設計になっている。非対話実行にはその次の turn が無い —— 実行モデルの前提の相違である。

### 回避策 2 つのうち、skill 側が採れるのは 1 つだけ

resume 時に次の 2 つを足したところ 4 本とも完走した（レビュー 6 件・インラインコメント 10 件まで到達）。

1. `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0` の指定
2. プロンプトへの「バックグラウンドの結果待ちで turn を終えない。待機はこの turn の中で完結させる」の明記

**どちらが効いたかは分離されていない。** 2 つを同時に入れた 4 本が完走した、という結果しかない。

## なぜ環境変数（1）を規範に書かないか

**理由は 2 つある。理由 A だけで決まる。**

**理由 A: skill には設定する手段が無い（決定的）。** 環境変数は**プロセス起動時に決まる**。`pr-workflow` は
既に起動しているプロセスの中で動くので、自分の `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` を設定できない。
設定できるのは起動側（`fh session launch` / `wave-orchestrator`）だけである。**skill 側の手段になりえない。**
この理由は変数が文書化されているかどうかと無関係に成立する。

**理由 B: 効果が分離できていない。** 1 と 2 を同時に入れた観測しかなく、**2 だけで足りる可能性が
排除されていない**。起動側で採るとしても、先に分離実験を通すのが順序として正しい。

起動側で 1 を使うかどうかは別の判断であり、`wave-orchestrator` の領分（#615）。

### 撤回した理由: 「未文書である」

**この主張は誤りだったので撤回する。** 経緯を残す —— 同じ誤り方をもう一度しないため。

当初は「[実測 2026-09-02] claude v2.1.258 のバイナリに名前は実在する
（`strings -a "$(mise which claude)" | grep -c PRINT_BG_WAIT_CEILING` → `5`）が、`claude --help` には
1 件も現れない（同じ走査での grep 件数 `0`）」を根拠に、**未文書の内部変数**と断定していた。

**走査結果は正しく、そこから引いた結論が誤っていた。** `--help` は**フラグ**の一覧であって環境変数を
列挙しない。「`--help` に無い」は「文書化されていない」の証拠にならない。

**一次ソース**: 本リポジトリの `.claude/prds/526-noninteractive-mode-research.prd.md`（`status: finalized`。
AC-007 で「すべてが一次ソースで裏取りされる」ことを品質基準に掲げた調査）§1.3 が、同じ変数を
**［原文］**（＝公式ドキュメント由来）タグ付きで記録している:

> **background subagent の待ち**［原文］: `claude -p` は background subagent の完了を待つが、既定で
> 10 分上限（`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`、`0` で無制限）。**`multi-review` のように 10 分超の
> leg を持つ処理では要調整。**

付録 B（参照した一次ソース一覧）は、この節の出典を公式ドキュメントの `headless`（"background task の
扱い"）としている。**526.prd は #585 と同種の懸念（`multi-review` が 10 分上限に触れうる）を、本 skill が
それを事故として観測するより前に指摘していた。** 本ファイルの「turn 内で待つための実測」表にある
「1 回の前景待機は最大 10 分」も、由来はこの同じ 10 分である。

**教訓**: 「無いことの証明」は、探した場所が網羅的であることを先に示さないと成立しない。
`--help` は網羅ではなかった。

## なぜ実行形態で分岐しないか

「非対話なら turn 内で完結させる / 対話ならバックグラウンドに回す」という分岐を作らなかった。

**理由 1: 判定手段の安定性を裏取りできていない。** [実測 2026-09-02] `fh session launch` の子の環境には
`CLAUDECODE=1` / `CLAUDE_CODE_ENTRYPOINT=sdk-cli` / `CLAUDE_CODE_CHILD_SESSION=1` がある。
**値が観測できることと、その値が契約であることは別である** —— これらが「非対話の子」を表すと公式に
約束されている裏を取れていない以上、名前も値も予告なく変わりうる。判定を根拠にした分岐は、判定が
黙って壊れた瞬間に**壊れた側（turn を跨いで待つ側）へ倒れる**。

（この「裏取りできていない」は「文書に無い」の言い換えではない。上の「撤回した理由」で踏んだのが
まさにその取り違えで、探していない場所を「無い」と読んだ。ここで言えるのは**まだ確かめていない**
までであり、それでも次の 2 つの理由で分岐そのものが要らないので、確かめる必要が生じない。）

**理由 2: 分岐が要らない。** 「turn を終えてよいのは `AskUserQuestion` のときだけ」は対話セッションでも
そのまま正しい。GATE 1・GATE 3 は `AskUserQuestion` なので例外側に入り、対話時の挙動は変わらない。
Phase 5 → 6 → 7 は元々直列なので、待っている間に親がやれる作業も無い。**分岐しないほうが、
規範としても短い。**

**理由 3: fail-safe の向きが逆になる。** 分岐を書くと、判定に失敗した子は「対話だと思って背景に回す」
= #585 の再演になる。分岐を書かなければ、最悪でも対話セッションが少し待つだけで済む。

## turn 内で待つための実測（ツールの挙動）

[実測 2026-09-02・本セッション（`fh session launch` の子）]

| 事実 | 意味 |
|---|---|
| 前景の `sleep 3` は通る（開始と終了の `date +%s` が 3 秒差） | ポーリングループを前景 Bash で書ける |
| Bash ツールの `timeout` は既定 120000 ms・**最大 600000 ms** | **1 回の前景待機は最大 10 分で切れる**。それより長い待機は tool call の繰り返しで作る |
| `Agent` ツールは**既定でバックグラウンド実行**（`run_in_background` の既定が true）で、完了は「通知」で届く | 明示的に `run_in_background: false` を渡さないと、サブエージェントの結果待ちがそのまま次 turn 待ちになる |
| `TaskOutput`（`block: true`）は turn 内で join できるが、ツール説明に **DEPRECATED** と明記されている | 待機の主手段にしない。非推奨のツール名に規範を載せると、廃止時に規範ごと失効する |

**「時間切れ = 待機の終わり」ではない。** 10 分の上限は tool call 1 回の上限であって、turn の上限では
ない。時間切れたら**同じ turn の中で待機コマンドをもう一度呼ぶ**。turn を終えて通知を待つのと、
tool call を繰り返して待つのは、外形が似ていてもまったく別の行為である —— 前者には続きが無い。

## なぜ (a) を採ったか（方向性 3 案の判断）

issue #585 は 3 つの方向性を挙げていた。

| 案 | 判断 | 理由 |
|---|---|---|
| **(a) 非対話の子向けに turn 内で完結する変種を定義する** | **採用（ただし「変種」にはしない）** | 前提の相違は `pr-workflow` 側にある。規範を Phase の隣に置ける。ただし別 path を増やすと 2 つの path が drift するので、**変種ではなく全 path に効く不変条件**として書いた |
| (b) レビューの統合・裁定を親が帯域外で担う | 不採用 | 親側の実行形態の定義（`wave-orchestrator` + `frontier-harness`）が要り、本 issue の scope 外。さらに **`pr-workflow` 自身は直らない** —— `wave-orchestrator` を経由しない `claude -p` からの起動は同じ壊れ方をする |
| (c) 起動側のプロンプト規約とフラグだけで閉じる | **部分採用（起動側は #615 へ）** | 規範が、それが統べる Phase から離れた場所（起動プロンプト）に住む。起動側が 1 つとは限らず、`pr-workflow` は依然として「次の turn がある」前提で書かれたままになる。ただし**子の自己検査だけでは塞がらない**部分（規範ごと飛ばされた場合）は起動側にしか置けないので、そこは #615 へ渡した |

**(a) を「変種」として実装しなかったことが要点である。** 非対話専用の path を足すと、対話 path と
2 本になり、どちらかにだけ入った修正が drift する。実行形態に依らず正しい不変条件として書けば
path は 1 本のままで済む（上記「なぜ実行形態で分岐しないか」）。

## 到達点検査を「子の自己検査」に留めた理由と、その限界

規範を足すなら、守られなかったことを検出できる形にする必要がある。

**子の側でできること**: GATE 3 の直前に PR の外形（`reviews` の件数・CI の結論）を見て、
Phase 6 に届いていなければ GATE 3 へ進まない。自己申告ではなく外部状態を見るので、
「レビューしたつもり」では通らない。#585 の 3 本はいずれも自己申告と外形が食い違っていた。

**子の側でできないこと**: 規範ごと飛ばされた場合、この検査も一緒に飛ぶ。**自己検査は自己申告よりは
強いが、外部からの検証の代わりにはならない。**

**#573 の検出との接続点**: `fh session --gate` は完了条件を `verification_results` へ連結し、
`fh runs` の `verification.total` から「gate を何本通したか」を読めるようにした。ただし
`--gate` に載せられるのは承認可能な形のコマンド（`manifest-policy.mjs` の `APPROVABLE_COMMAND`：
`npm run` / `pnpm run` / `yarn run` / `bun run` / `uv run` / `pytest` / `go test` / `cargo test`）に
限られ、`gh pr view ...` を直接は載せられない。**到達点の検査を gate に載せるには、リポジトリ側で
タスクランナーの script に包む必要がある** —— これは起動側とリポジトリ側の領分なので #615 へ渡した。

`verification.total` が 0 でないことは「gate を通した」ことしか意味せず、**どの Phase まで届いたかは
PR の外形からしか読めない**。両者は別の信号であり、片方で他方を代替しない。
