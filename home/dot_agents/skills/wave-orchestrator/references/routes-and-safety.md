# wave-orchestrator: 2 経路の並存と安全原則の根拠

これは**根拠**である。守るべきこと（規範）は [`../SKILL.md`](../SKILL.md) が持つ。ここにあるのは
その規範がなぜその形なのか —— 実測と、一度踏んだ事故の経緯 —— で、**規範を疑う / 書き換える /
規範が想定していない状況に出たときに読む**。

対応する規範: `SKILL.md`「経路は 2 つある（既定は承認チャネル）」「安全原則（絶対遵守）」。

## なぜ新規の wave は承認チャネル経路なのか

画面を読まず、キーを送らず、「今まさに未回答か」を推定しない —— **呼ばれた時点が未回答であり、
返り値が回答である**（#529 PRD §1.2.3 実測）。送信先ペインの取り違え、プレースホルダの誤読、
Esc 固着、確定キーの投機送信は、この経路には**構造的に存在しない**。tmux 経路が積み上げた検知
まわりのガードは、防いでいた事故が起こりえないので不要になる。

**tmux を捨てるわけではない。** 実行を非対話にしても、ペインで `fh session` を走らせれば
「人が覗いて介入できる窓」は残る（#529 PRD §6 ガード 21）。詰まったときは控えてある session id で
`claude --resume <session-id>` を対話セッションとして開き直せる。

## フォールバックを禁じる理由

`fh session` が exit 2 を返す・`fh doctor` が `unavailable` を返す等で起動できないとき、legacy 経路へ
フォールバックしてはならない。フォールバックは **#537 が排した経路を裏口から復活させる**ことであり、
しかも**最も検証が届いていない状況（`fh` が壊れているとき）で発動する**。

## legacy 経路のスクリプトと撤去条件

`scripts/wave-events.sh` / `scripts/send-to-pane.sh` は 2 本とも撤去が決まっている。#539 が決定と
撤去条件を確定した（`.claude/prds/539-tmux-path-retirement-criteria.prd.md`）。tmux 自体は残す ——
撤去するのは「機械が画面を読んでキーを送る導線」であって、「人が覗いて介入する導線」
（ペイン ＋ `claude --resume`）ではない。

**legacy 経路のガードには既知の穴が 2 件あり、直さないことが決定済み**（PRD D2）。

1. `send-to-pane.sh` の `question_ui_open()` は**固定文字列 2 個のホワイトリスト**で、TUI の文言が
   変われば判定が静かに default-allow 側へ倒れる。
2. **multiSelect の問いを完了させる経路が無い。**

**規範 1（新規は承認チャネル）と規範 2（legacy は drain-only）が、この 2 件の唯一の緩和策である。**

**撤去の順序は「実運用データ → 走行中の wave が無いことの確認 → スクリプト撤去 → `settings.json` の
hook 配線を外す」。** 逆順にすると、記録が空のまま `wave-events.sh` が `UNKNOWN` を返し続け、
「検知器が壊れた」と「誰も停止していない」が区別できなくなる（安全原則 4）。撤去条件（G1〜G6）と
その根拠は PRD 側にある。

## 安全原則それぞれの事故記録

### 1. マージは代理しない

これは分類器が上書きできない無条件エスカレート集合の筆頭であり、実際に**「重複投入された古い
セッションが merge gate を経ずに無断マージした」事故が起きている**。経路が変わってもこの原則は
動かない。

承認チャネル経路では `approval-rules-baseline.mjs` の deny ルール（`git-merge` / `gh-pr-merge` /
`gh-release` / `package-publish` / `git-force-push` / `git-history-rewrite` 等）が子の側で escalation を
起こし、要求は `fh approvals` に積まれる。**そこで Leader が `fh approve --allow` を打ってはならない**
—— 承認チャネルは要求を user へ運ぶ経路であって、Leader が代理で許可してよいという意味ではない。

**これはコードではなく方針で担保している**（Leader 自身は承認チャネルの下では走っていないため、
Leader の `fh approve` を機械的に止める層は無い）。したがって規範を緩めた瞬間に防壁が消える。

### 2. 状態を分類していないペインへ送信しない

tmux 経路の原則。承認チャネル経路では「送信先」という概念が無いので不要化する。一斉配信であっても
1 ペインずつ分類する。**選択肢が開いているペインへ確定キーを送ると、誰も答えていないのに
「ユーザー承認済み」という記録が成果物に残る。実際に起きた。**

### 3. 事実主張に依存する問いは自動応答しない

セッションの自己診断は外れる。「既存 flaky です」「base 側の既存違反です」「本 PR と接点ありません」
—— **いずれも実運用で覆っており、そのまま承認していれば実在する回帰を見逃していた。**
検証の具体的な当て方は [`verification.md`](verification.md) が持つ。

### 4. 検知器が自己診断に失敗したら黙って進まない

検知の静かな故障は「誰も停止していない」と見分けがつかず、全セッションが止まったまま気づけない。
この原則が具体的にどう破られたかは [`approval-channel.md`](approval-channel.md)「self-check を
やり直す理由」にある（`2>/dev/null || true` がパース失敗を「イベント無し」へ写像した実測）。

### 5. 共有リポジトリの git 操作を子にやらせない

複数セッションが同時に既定ブランチを更新すると**ロック競合する**。orchestrator が直列に 1 回だけ行う。
