# wave-orchestrator: 代理応答の判定と成果物の検証の根拠

これは**根拠**である。守るべきこと（規範）は [`../SKILL.md`](../SKILL.md) が持つ。ここにあるのは
その規範がなぜその形なのか —— 実測と、一度踏んだ事故の経緯 —— で、**規範を疑う / 書き換える /
規範が想定していない状況に出たときに読む**。

対応する規範: `SKILL.md`「代理応答の判定（両経路に共通）」「成果物の検証」。

## 一次ソース検証が要る事実主張

セッションの自己診断は外れる。実運用で覆った主張と、その当て方:

- **「これは既存の flaky です」** → 失敗は断続的か。同一テストが連続で落ちていないか。その spec は
  本当に変更範囲に触れていないか（**共有 seed ヘルパー経由で触れている**ことがある）。
- **「base 側の既存の問題です」** → base で実際に再現するか。ブランチが古いだけではないか。
- **「◯◯が存在しません」** → 実際に見に行く。不在の主張は特に疑う。
- **「レビュー指摘に対応済みです」** → 対応したはずのコミットが主張どおりの内容か。

### 不在主張は Leader 自身にも当てはまる

[実測] 子の「未定義トークンが N 箇所ある」を検算して「1 種だけ 0 件」と読み、**存在しない欠陥を
断定して差し戻した**。実際は検索側が沈黙しており、子が正しかった（生 NUL を含むソースを `grep` が
無言で飛ばす。グローバル `CLAUDE.md`「grep が無言でスキップするもの」を参照）。

**子を反証するときこそ、自分の検索手段が沈黙していないかを先に疑う。**

### 検証で覆ったときに訂正を届ける経路

提示された選択肢が両方とも間違っていることがある。承認チャネルでこれを行う経路は
**`fh approve --deny --message`** ひとつしかない（allow は自由文を運べない。機序は
[`approval-channel.md`](approval-channel.md)「allow が自由文を運べないことの実測」）。

## 5 項目を満たしても取れない欠陥

[実測] 全長完走・CI green・レビュー 6 件対応済み・5 項目すべて green の PR をマージした直後、
user が実機で欠陥を見つけた。**リストを埋めた時点で検証が終わったと読まない。**

すり抜けた構造は再現性がある。変更範囲は画面上の 1 要素で、テストは SSR・dom・a11y のいずれも
**その要素が描画された前提**で書かれていた。**「その要素にそもそも到達できるか」は、その要素の
テストからは原理的に見えない。** レビューも diff の範囲を見るので、**diff の外にある呼び出し側の
条件**には届かない（原因行は別 PR 由来の既存欠陥で、当該 PR はそのファイルを 1 行も触っていない）。

だから受け入れ条件を、実装した層ではなく**利用者の到達経路**で言い直す。今回なら「文言が直ったか」
ではなく「**その画面に着けるか**」。

**この問いに Leader が毎回答えられるとは限らない**（実機・サインイン・本番データが要る）。
答えられないことを隠して規約にすると、守られない規約が 1 つ増えるだけである。静的検証の担当範囲を
正しく宣言し、その外側は判断点として user に渡すのが、リストを増やすより確かである。

## 子が gate を通ったかを引く 2 信号と、その弱点

[実測] `fh runs` の記録が完走した子と**外形が完全に一致**した（status / exitCode / denials すべて）
なかで、判別できたのは次の 2 点だけだった。

| 見るもの | 何の証拠か | 単独での弱点 |
|---|---|---|
| `gh pr view <n> --json reviews` が **0** | レビューが投稿されていない**直接の証拠** | 投稿形式に依存する（同じ波でも 1〜10 とばらついた） |
| 全コミットの `committedDate` が **PR 作成時刻より前** | PR 作成後に 1 度もコミットしていない = 指摘対応が回っていない | **レビューが 0 件だった場合にも成立する**。加えて下記のとおり rebase で無効化される |

### 信号 (2) は rebase で無効化される（fail-open）

**`committedDate` は committer date であって author date ではない。** `git rebase` は replay した
全コミットに**新しい committer date を打ち直す**（author date は保つ）。実測:

```
before rebase   author=2020-01-01T00:00:00Z  committer=2020-01-01T00:00:00Z
after  rebase   author=2020-01-01T00:00:00Z  committer=<rebase を打った時刻>
```

したがって **base へ追従するために rebase した PR では、全コミットが「PR 作成後」に見える**。
信号 (2) は常に偽になり、2 信号の AND は成立しなくなる。

**倒れる向きが悪い。** 判定は「レビューを通していない」と言えなくなる側 —— つまり
**「対応した」側（fail-open）** へ倒れる。#573 が扱う「`succeeded` を完了と読まない」と同じ
沈黙する故障の形で、**rebase したという理由だけで検査が無言で通る**。

だから規範側は、rebase 済みの PR で信号 (2) を根拠に使うことを禁じ、**判定不能として user へ
上げる**ことにしてある。`git log --format=%aI`（author date）で代替する案もあるが、author date は
cherry-pick や `--amend --date` で任意に設定でき、squash merge のリポジトリでは PR 内の履歴が
そもそも潰れるため、**信号として信頼できる補強にならない**。コミット時刻に依存しない判定は
#615（#617 待ちでブロック中）が扱う。
