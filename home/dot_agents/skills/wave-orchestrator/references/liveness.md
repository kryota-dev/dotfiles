# wave-orchestrator: 生存判定と結末確認の根拠

これは**根拠**である。守るべきこと（規範）は [`../SKILL.md`](../SKILL.md) が持つ。ここにあるのは
その規範がなぜその形なのか —— 実測と、一度踏んだ事故の経緯 —— で、**規範を疑う / 書き換える /
規範が想定していない状況に出たときに読む**。

対応する規範: `SKILL.md`「沈黙ストールは別経路で見張る」。**生存判定のコマンド形を組み直すときは、
先にこのファイルを読むこと。** 穴は 7 つあり、いずれも fail-open（止まっているのに「稼働中」と読む、
あるいは動いていないものを数える）方向へ倒れる。

## スナップショットを先に取る理由

**`grep -v grep` を使わない。2 段とも必要である。** [実測] スナップショットを取らずに
`ps | grep | ...` と直結すると、**パイプライン中の `grep` 自身がスナップショットに写り込む**
（`awk -v self=$$` を足しても 2 件残った）。先にスナップショットを取ればフィルタのプロセスはまだ
存在せず、`$$` の除外で囲みのシェル自身も消えて 0 件になる。

## 7 つの穴

### 1. `pgrep -f` を生存判定の土台にしない

[実測] `pgrep -f` は**現セッションの祖先プロセスを一切返さない** —— `pgrep -f 'installs/claud[e]'` が
43 件（他セッションの `claude` を含む）を返しながら、**自分の親 `claude` だけが欠ける**。同じ
プロセスを `ps -Ao pid=,command= | grep` は見つける。「見えないプロセス集合がある」道具を生存判定の
土台に置くと、その集合に入ったものが常に「いない」と読まれる。**`ps` は同じ盲点を持たない。**

### 2. パターンを固定文字列にする（`grep -F`）

ワークツリーの絶対パスを正規表現へ素で埋めると、パスに含まれる `.` などが誤爆する。`-F` なら
escape を考えずに済み、`pgrep` で必要だった角括弧の小細工も要らなくなる。

### 3. ワークツリーの絶対パスで絞る。ただしパスだけで絞ってもいけない

マシン全体が見えることを前提に絞らないと、**別リポジトリの wave の子まで数える** —— 実測で、
他リポジトリの 3 本が混ざり自分の 4 本が 7 本に見えた。件数で判断する監視は、これで静かに壊れる。

**ただしワークツリーのパスだけで絞ってもいけない。** 子が起こす vitest / tsc などの子孫プロセスも
同じパスを argv に持つので、[実測] 件数が `2 → 1 → 2` と揺れた。**`cli.mjs session` との AND** で、
fh のプロセスだけに絞る（規範のコマンドが `grep` を 2 段重ねているのはこのため。1 段に簡略化しない）。
揺れの向きは「多く数える」で危険側ではないが、**揺れる監視は使われなくなる**ので、結果として監視が
無くなる方向に効く。

### 4. tmux の `pane_current_command` を判定に使わない

`fh` が node を exec しても `zsh` と報告することがあり、当てにならない。プロセスを直接見る。

### 5. 監視自身がマッチする書き方をしない

**`ps` は `pgrep` と違って呼び出し側の argv も見える。** パターンを argv に載せるとその行が自分に
当たる。[実測] 監視の最終段を `grep -cF` にしたところ、子が 0 本でも件数が 0 にならなかった。

**壊れ方の向きが最悪である** —— 常に 1 以上を返すので、**子が全部死んでも「全子終了」が永遠に
発火しない**（他の穴は「見落とす」側で、承認要求なら 8 時間で自動 deny に着地する。これだけは
着地しない）。

### 6. `grep -v grep` で自分を落とさない

[実測] `claude -p` の **argv にはプロンプト全文が載る**ため、プロンプトに `grep` の語が入っていると
**子プロセス自身が `grep -v grep` の網に掛かって消える**（argv に `grep` を含むプロセスで
4 件 → 0 件）。`fh` のプロセス（argv が短く固定）には無害だが、**孤児化した `claude -p` を探す用途
では地雷**であり、**落ちる向きは「いない」** —— 見逃す方向にしか倒れない。自分の除外は語ではなく
**PID** で行う。

### 7. 判定スクリプトを、それを書いたのと同じ Bash 呼び出しで実行しない

[実測] ヒアドキュメントでスクリプトを書き、同じ呼び出しでドライランしたところ、**2 本の子が 4 本に
見えた**。Claude Code の Bash ツールはコマンド全体を `zsh -c '<全文>'` で走らせるため、**その
ラッパーの argv に「スクリプト全文（＝`grep` パターン）」と「ワークツリーの絶対パス」が同居する**。
2 段の `grep` が両方ともこの 1 行に当たり、ワークツリーごとに 1 件ずつ二重計上された。

**`awk -v self=$$` では消えない** —— 犯人は `$$`（スクリプト自身）ではなく**祖先プロセス**である。
穴 5 の変種だが、除外の当てどころが違うので別項にする。向きは「多く数える」なので危険側では
ないが、**件数の検算を信用できなくする**。スクリプトの作成と実行を別の呼び出しに分けるか、
PID 直接照会を使う。

## `claude -p` の子を argv で引かない理由

argv がプロンプト全文である以上、**そこに現れる任意の語が偽陽性と偽陰性の両方を生む**（[実測]
プロンプトに書いた issue 番号が別の子の argv に一致して誤検出した）。argv にはワークツリーのパスが
載らない一方、プロンプト由来の無関係な語は載る。**argv マッチは両方向に外れる。**

## PID 直接照会が確実である理由

起動時に控えた PID に `ps -p` を当てると、返るのはその 1 プロセスの行だけなので、**自己混入が
構造的に起きない**。

この PID は**監視の持ち物**であって、「中断と再開」節が禁じている state file ではない（再開に要るのは
session id 1 点で、そこは変わらない）。監視が落ちたら PID も捨て、パターン照合の形で組み直す。

照合先を `fh` のプロセスにするのは、それが**子の実行中ずっと生きている親**だからである（launcher が
`exec node <...>/frontier-harness/cli.mjs "$@"` するので、argv に
`frontier-harness/cli.mjs session ... --worktree <abs>` がそのまま載る）。

## 件数の検算を入れる理由

上の穴はいずれも件数のずれとして最初に現れるので、検算があればループの初回で捕まる
（`SKILL.md` legacy 節の「書いたら本番に流す前にドライランする」と同じ理由）。

## `fh runs` が結末を持つ

`fh status` は route 決定（何を選んだか）しか持たず、結末（どう終わったか）は別コマンドである。
`fh runs --json` が新しい順に status / exitCode / failureReason / 時刻を返し、`--run <adapterRunId>` で
1 件を引ける。**起動時 JSON を流したスクロールバックを失っても結末は残る** —— 並列で回すほどこれが
効く。ただし `resumeKey` / `denials` は記録されないので、**session id は従来どおり起動時に控える**。

## `succeeded` を「作業が完了した」と読まない理由（#573）

`fh session` の `outcome` が表すのは**ターンがエラーなく完了したか**だけで、子が指示された gate
（レビュー・検証コマンド等）を 1 度も通していなくても `succeeded` / `exitCode: 0` になる。
`adapter-claude` の結果解釈が見るのは「最後の result イベントの `is_error`」と「プロセスの終了コード」
で、**子が何をしたかは見ていない**。

[実測] wave 4 本のうち 3 本が「CI の完了通知が来次第レビューへ進みます」と述べて turn を終えた。
`fh session launch` は 1 turn 実行なのでその通知は来ず、**PR は立ったがレビュー 0 件**で終了した。
3 本とも `fh runs` の記録は `succeeded` / `exitCode: 0` で、**完走した子と外形が一致していた**。
`denials` も空である（子は拒否されたのではなく、単に「やらなかった」ため）。

harness の記録だけで判別できるようにするのは #573 の対象で、それまでは成果物側との二重確認が
唯一の防御線である（当て方は [`verification.md`](verification.md)）。なお `pr-workflow` を非対話の
子に走らせること自体の噛み合わなさは #585 で扱う。
