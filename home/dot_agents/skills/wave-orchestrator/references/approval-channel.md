# wave-orchestrator: 承認チャネル監視の根拠

これは**根拠**である。守るべきこと（規範）は [`../SKILL.md`](../SKILL.md) が持つ。ここにあるのは
その規範がなぜその形なのか —— 実測と、一度踏んだ事故の経緯 —— で、**規範を疑う / 書き換える /
規範が想定していない状況に出たときに読む**。

対応する規範: `SKILL.md`「Phase 3: 監視と代理応答」→「承認チャネル経由（既定）」。

## 「状態の推定」だけが不要になる

承認が要る操作と `AskUserQuestion` は、子から**同期的な MCP ツール呼び出し**として承認チャネルへ
届く。tmux 経路が積み上げた検知まわりのガード（到着順非依存の集合演算、`UNKNOWN` の扱い、壊れた
JSONL 行の降格、self-check）は、この経路では**防いでいた事故が起こりえないので不要になる**。

**不要になるのは「状態の推定」だけである。** 要求が積まれたことは**こちらへ通知されない**ので、
見に行く義務は残る。この節を「監視不要」と読んで放置した実例があるため、規範側に明示してある。

## 通知が飛ばないことの実害

[実測] 承認要求を **27 分放置**し、user に指摘されるまで気づかなかった。前景で別の作業をしていると、
そのまま止まったことに気づかない。

**放置は「通る」ではなく「止まる」。** 上限（既定 8 時間）に達した要求は自動で deny になるので、
気づかないまま時間が過ぎると、子は拒否されて先へ進む。

**監視に失敗側を入れる理由**: 新規の承認要求 ID だけを見ると、**子が死んで要求が来なくなった状態が
「静かで順調」に見える**。子プロセスの数の変化（[`liveness.md`](liveness.md) の生存判定）を同じ
仕掛けに含めることで、**沈黙が成功に見えないようにする**。

## `skipped` を読み飛ばしてはいけない機序

`skipped` は**壊れて読めなかった要求ファイルの隔離先**で、**そこに入った要求は `approvals` に
現れない**（1 件の破損で一覧全体が読めなくなることを避ける設計）。`.approvals[]` だけを見る監視は、
**壊れた要求を静かに取りこぼす**。

出力が要求の配列ではなく envelope（`{"approvals": [...], "skipped": [...]}`）なのも同じ設計に由来する。
top-level を配列として舐める jq は**型エラーで落ちる**。

## self-check が要る理由（42 分の事故）

**「引く仕掛けを用意した」だけでは足りない。** [実測] 仕掛けを用意した wave で、承認要求 2 件を
最大 **42 分**放置した。jq が envelope を舐められず型エラーで落ちていたのだが、
`2>/dev/null || true` と組み合わさって**「承認要求 0 件」と区別できない空文字列**を返し続けていた。
監視は全期間 armed で、外形上は正常に見えていた。

これは legacy（tmux）経路が `--self-check` で塞いでいた穴と同じものである。「状態を推定しない」が
tmux 経路の検知ガードを不要としたのは**状態の推定について**であって、**Leader 側のポーリングは
依然として検知器であり、壊れる**。

### なぜ件数で測ってはいけないか

件数ベースの検査（「`--all` が 1 件以上返ること」）は Phase 4 の `fh approvals --purge` と正面から
矛盾する —— [実測] **後始末を規定どおり行った直後の新しい wave では `--all` が
`{"approvals":[],"skipped":[]}` を返すので必ず落ちる**。しかも落ち方が検知器の故障と同じ表示になる
ので、正常なのに「`fh` が壊れた」と誤診させる。

測りたいのは jq が envelope を舐められるかだけで、**台帳に記録があることは要件ではない**
（実際に起きた事故も、記録の不在ではなく型エラーだった）。件数ベースが使えるのは
**wave の途中で検知器を組み直すときのように、既知の件数を置ける場合**に限られる。

### なぜ失敗の種類を別の出口に分けるか

self-check の形が `||` を 3 段に割っているのは、「`fh` が落ちた」「jq が舐められない」「形が違う」を
別々のメッセージにするためである。`[ "$n" -ge 1 ]` のような単一の判定は、`$n` が空文字（jq が落ちた
場合）だと zsh で引数エラーになり、**「壊れた」と「0 件」が同じ exit に落ちる** ——
「検知器のエラーを握り潰さない」を検査自身が破ることになる。

`2>/dev/null` と `|| true` の併用は、**パース失敗を「イベント無し」に写像する** —— 安全原則 4
（検知器が自己診断に失敗したら黙って進まない）の具体的な破り方である。抑止したいなら、
**エラーと 0 件を別の値で表す**こと。

### 組み直したら self-check をやり直す理由

上記の事故では、同じ turn の ad-hoc クエリが同型のエラーで落ちていたのに、**ad-hoc 側だけ直して
監視スクリプトを見に行かなかった**。組み直しは検知器を疑う機会であって、コピー元を信じる機会では
ない。

## allow が自由文を運べないことの実測

［実測 2026-08-30］承認サーバーを patch して allow の応答に `message` を載せても、子が受け取ったのは
次の 1 行だけだった。

```
Your questions have been answered: "続行しますか"="はい". You can now continue with these answers in mind.
```

**選択肢の `description` も、選ばれなかったラベルも配送されない。** 子が見るのは「どの問いに、
どのラベルが選ばれたか」だけである。したがって:

- **選択肢のラベルに意味を載せる。** 子が受け取る唯一の情報がラベルなので、`はい` / `いいえ` の
  ようなラベルしか無い問いには、判断の理由を伝える術が無い。
- **訂正を届けたいなら `--deny --message` を使う。** 意味的には差し戻しなので deny で正しい。冒頭に
  「これは拒否ではなく差し戻しである」と書いておくと、子が要求そのものを取り下げずに済む。

`--message` を `--allow` に付けると `fh approve` が落ちるのは、**配送できないものを黙って捨てると、
届いた前提で監視を続けてしまうため**である。

また `deny` は子側で `permission_denials[]` に残るので、**拒否した事実が機械可読な記録になる**
（tmux 経路では記録が残らなかった）。

## 待たせられる時間の機序

承認チャネルは同期呼び出しなので、user へ上げている間**子はブロックする**。既定で 8 時間まで
保持でき、その間 **60 秒ごとに progress 通知が飛んで stdio の idle timeout をリセットする**。

**この既定値を skill 側で再定義しない**理由: `fh session` は `--timeout-ms` /
`--progress-interval-ms` を渡されたときだけ承認 server へ素通しするので、skill 側の再定義は
SSOT を 2 つにするだけで実効を持たない。
