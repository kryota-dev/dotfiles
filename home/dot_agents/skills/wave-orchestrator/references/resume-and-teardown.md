# wave-orchestrator: 中断と再開・後始末の根拠

これは**根拠**である。守るべきこと（規範）は [`../SKILL.md`](../SKILL.md) が持つ。ここにあるのは
その規範がなぜその形なのか —— 実測と、一度踏んだ事故の経緯 —— で、**規範を疑う / 書き換える /
規範が想定していない状況に出たときに読む**。

対応する規範: `SKILL.md`「中断と再開」「Phase 4: 後始末」。

## 再開で環境が真実を持たなくなる

quota が閾値帯に達したら止めて次のウィンドウで再開する、というのは quota 節が示唆する正常な運用で
あって例外ではない。落とし穴は**環境が真実を持たなくなる**ことにある。

**採番するのは Leader なので、記録は起動の時点で済ませられる。** `ps` の argv を読みに行く必要は
無く、「停止したら情報源が消える」という順序の問題そのものが無くなる。`fh session launch` は採番した
値を起動直後に stderr へ出し、完走時の JSON にも `sessionId` / `resumeKey` として載せる。

`fh session resume --resume-key <id>` では起動時検査・承認チャネルの配線・sandbox policy が launch と
同じ順序・同じ形で適用される（弱まらない）。

## resume でも監視を arm し直す理由

[実測] 正常終端したあと resume して arm し直さず、その状態で「進捗が出たら報告します」と書いた。
**報告経路は存在しなかった。** resume は launch と同じく「子が走り出す」操作なので、監視の必要性は
変わらない。**前の監視が子の終了で正常終端していることに注意する。**

resume は「起動する」節から離れた場所にあるため、「起動したら監視」の連想が働きにくい。これが
規範側で resume にも明示的に arm を課している理由である。

## `--capability` が resume で継承されない

[実測] `--capability` を省いた resume は既定（`session.child`）で記録され、**launch 時の tier 選択が
消える**。launch と resume は同じ行でフラグを読むだけで、**resume-key から元の capability を引く
経路が無い**。

現行 registry では既定が最も強い（Opus @ xhigh）ので**フォールバックは上振れ**し、floor は下回らない。
ただし**その前提に寄りかからない** —— 上振れは quota をそのまま浪費するし、既定より弱い capability が
既定になれば向きが反転する。

## ペインの外から resume すると窓を失う

［実測 2026-09-02］ペインの外から resume したところ、子は正常に動いていたのに**ペインには前の
セッションの終了時 JSON が残り続けた**。user が画面を見て「止まっているようですが、何故ですか」と
問うた。

**ペインは空白にならない** —— もっともらしい終了の痕跡を表示し続けるので、**「正常に終了した子」と
「窓を失った稼働中の子」が画面上で区別できない**。これは「プレースホルダの誤読」と同じ形で、今回は
人が誤読した。

## 長い中断は「通った」ではなく「拒否されて止まった」

承認要求は既定 8 時間で自動 deny になるので、長く放置した wave は「通った」ではなく「拒否されて
止まった」状態になっている。再開前に決着を確認する理由がこれである。

人が直接介入したいときに `claude --resume <session-id>` で対話セッションとして開き直せるのは、
**別ディレクトリからでも文脈を保って再開できる**ため（#526 §1.3 実測）。

## `fh` のプロセスを撃つと監督者だけが死ぬ

[実測] `fh session launch` の PID に `SIGTERM` を送ったところ、**`fh` だけが死に、その下の
`claude -p` は `ppid=1` へ reparent されて 14 時間走り続けた**。失うものが 3 つある。

1. **user の窓。** ペインに出ている `frontier-harness: child event ...` は `fh` の出力なので、撃った
   瞬間にペインが固まり、**子が何をしていても一切見えなくなる**。tmux を残す理由（「人が覗いて
   介入できる窓」）を、停止操作そのものが壊す。
2. **harness の実行記録。** `fh` が結末を書く前に死ぬので、**`fh runs` にその run が 1 件も残らない**。
   同じ wave で自然終了した子は `succeeded` / `exitCode` / 時刻まで記録されており、**差は
   「`fh` を撃ったかどうか」だけ**だった。この run がどう終わったかを引く手段はもう無い。
3. **監督。** 承認サーバは `claude -p` の子なので生き残り、要求は届き続ける。**「問えるが監督されて
   いない」**状態になり、外形が正常に見えるため誤報告を招く。

worker（`claude -p`）かプロセスツリー全体を撃てば、`fh` が子の終了を観測して結末を記録し、最終 JSON
をペインに残して自分も終わる。**記録も窓も保たれる。**

**「身元を確認する」は撃つ対象が正しいことを保証しない。** 上の事故では argv の label を確認して
おり、`fh` は確かに対象のプロセスだった。**確認すべきは「これは監督者か worker か」である。**

**停止の完了を `ps` で判定しない理由**: 監督者しか見ていないので、孤児が残っていても消えたように
見える。

なお `fh` には stop / kill / cancel に相当するサブコマンドが無い（`session` は launch と resume だけ）。
**正規の停止手段が無いので、シグナルを撃つ側が上記を守るしかない。**

## 会話内容をどこまで消すか

承認要求の payload には**質問文と選択肢が入っている**（答えるために必要だが、wave が終わったあとまで
残す理由が無い）。`fh approvals --purge` は決着済みだけを消す。pending は消えない —— まだ答えていない
問いがあるなら、それは掃除ではなく対応の対象である。

**実行記録は残る。** `adapter_runs` と evidence には capability / provider / model / effort / 状態 /
時刻 / exit code / resume key / 拒否されたツール**名** だけが入り、**会話内容は入らない**（設計上
そうなっている。prompt もファイル経由で渡すので記録側に触れない）。保持期間は `fh clean` の
retention に従う。
