# wave-orchestrator

`pr-workflow` は単一タスクを**深く**回す。`issue-fleet` は複数 issue を**浅く広く**回す（サブエージェント、
draft PR 止まり）。本 skill はその中間にない第三の象限 —— **深く × 広く** —— を担う。

実行単位が違うことが本質。`issue-fleet` はサブエージェントに委任するので親のコンテキストを共有し、
親が尽きれば全部止まる。本 skill は**独立した CLI セッション**を立てるので、各セッションが自分の
コンテキストを持ち、自分の gate を通り、自分でレビュー対応まで走る。その代わり、セッションは
対話を求めて止まる。**その停止をどう捌くかがこの skill の中核**になる。

## 引数

| 引数 | 既定 | 意味 |
|------|------|------|
| `<issue 番号列>` | - | 対象 issue。空白区切り。`#` は付けても付けなくてよい |
| `--from-radar` | off | `repo-radar` の直近の出力を入力に取る（issue 番号列の代わり） |
| `--max-parallel=N` | **4** | **同時に走らせる子セッション数の上限**。wave のサイズとは別物で、wave がこれを超えるなら分割して実行する。quota が閾値帯に入っているときは下方調整する |
| `--profile=<launcher>` | 親から継承 | 子セッションの launcher。親と異なる profile を指定した場合は user の明示承認を求める |
| `--dry-run` | off | Phase 1 で止め、計画と起動コマンドだけを返す |

## 安全原則（絶対遵守）

1. **マージは代理しない。** 常に user へ上げる。これは分類器が上書きできない無条件エスカレート集合の
   筆頭であり、実際に「重複投入された古いセッションが merge gate を経ずに無断マージした」事故が
   起きている。
2. **状態を分類していないペインへ送信しない。** 一斉配信であっても 1 ペインずつ分類する。選択肢が
   開いているペインへ確定キーを送ると、**誰も答えていないのに「ユーザー承認済み」という記録が
   成果物に残る**。実際に起きた。
3. **事実主張に依存する問いは、一次ソースで裏を取るまで自動応答しない。** セッションの自己診断は
   外れる。「既存 flaky です」「base 側の既存違反です」「本 PR と接点ありません」——いずれも実運用で
   覆っており、そのまま承認していれば実在する回帰を見逃していた。
4. **検知器が自己診断に失敗したら黙って進まない。** 検知の静かな故障は「誰も停止していない」と
   見分けがつかず、全セッションが止まったまま気づけない。
5. **共有リポジトリの git 操作を子にやらせない。** 複数セッションが同時に既定ブランチを更新すると
   ロック競合する。orchestrator が直列に 1 回だけ行う。

## Phase 0: 前提チェック

`tmux` の有無を確認する。**無ければ Phase 1 だけを実行して停止**し、生成したコマンド列を返す。
これは縮退ではなく正規の使い方で、user が手で起動する運用が成立する。

親の profile を `CLAUDE_CONFIG_DIR` の basename から導出し、子セッションの launcher を決める
（`~/.local/launchers/` の同名 symlink）。**親と異なる profile で起動するのは user が明示承認したときだけ**。
quota は profile ごとに独立プールなので「空いている方へ流す」最適化が構造的に可能だが、これは
**業務を別区分のアカウントで走らせることに直結する**ので自動ではやらない。

子には orchestrator 用の model variant を使わない。子は実行者であって orchestrator ではなく、
その variant は model floor を全て pass するため floor 判定が実質無効化される。

### tmux セッションの用意

**子セッションは専用の tmux セッションに置く。** user が普段使っているセッションへウィンドウを足すと、
無関係な作業と混在して監視も後始末もしづらくなる。

- **セッション名**: `wave-<owner>__<repo>`。区切りが `__` なのは `/` `#` `.` `:` が tmux の target 構文と
  衝突するため。owner/repo を含めることで、別リポジトリの wave と混線しない。
- **存在したら再利用し、絶対に kill しない。** 使い捨ての観測用セッションと違い、これは実作業をホストする。
  同名セッションの kill は稼働中の子を殺す。同名ウィンドウが既にあるなら、それは重複起動の兆候として扱う。
- **導線の提示**: tmux の外からは `tmux attach -t <name>`、tmux の中からは `tmux switch-client -t <name>`
  （入れ子 attach を避ける）。

ウィンドウ番号の詰め直し（`renumber-windows`）とペインタイトルの表示（`pane-border-status`）は
**利用者の tmux 設定に依存する**。skill 側では設定せず、必要なら利用者の設定で有効にしてもらう
（設定していない環境ではタイトルが見えないだけで、動作そのものは変わらない）。

## Phase 1: 棚卸しと wave 計画（tmux 不要）

`repo-radar` の出力があればそれを入力に取る。無ければ自分で集める。

1. **収集** — assign 済み open issue、自分の open PR、既存ワークツリー、稼働中セッション。
2. **内容の把握** — issue 本文を読む。**本文の前提は実装の進行で腐る**ので、issue が指摘した症状が
   今も再現するかをコードで確かめてから計画に載せる。「PR #NNN で外した」「定数 X が原因」といった
   断定は特に裏取りする価値がある。
3. **依存グラフ** — 決定待ち（needs-decision）が実装をブロックしていないか、親子・先行関係。
4. **コンフリクト分析** — **同じファイルを触る issue は同じ波に入れない**。ここが並列度を決める。
   判断材料は issue 本文ではなくコード（対象コンポーネント・共有ヘルパー・e2e）。
5. **他者の open PR との衝突確認** — 同じ領域を他メンバーが触っていないか。タイトルだけで判断せず
   変更ファイル一覧を見る。タイトルが似ていても実体は別物ということが普通に起きる。
6. **wave 割り** — 並列可能な組と、直列にせざるを得ない鎖を出す。**最長の鎖が全体の律速**なので、
   その先頭を最初の波に入れる。
7. **tier と model/effort** — tier ごとの model/effort は `/model-fitness-check` の contract に従う。
   **contract テーブルを本 skill に再掲しない**（SSOT が drift する）。floor を下回る model で
   起動する必要があるなら、user の明示承認を得たうえでプロンプトに事前承認ブロックを前置する。
   承認なしにこのブロックを付けない —— これは blocking gate を静かに無効化する仕組みだから。
8. **コマンド生成** — 1 セッション 1 コマンド。`--size` を pin する（tier 判定が session 内で揺れると
   floor 判定も揺れる）。プロンプトには次を含める:
   - 何をするか（issue 番号と一文要約）、`--size` / `--operation`
   - `<context>` 既に下した決定、腐っている前提の訂正、並行セッションとの衝突可能性
   - `<scope>` 対象外の明示。後続 issue へ送るものを名指しする
   - `<constraints>` 壊してはいけないもの（IPC 契約、a11y ラベル、既存のトレードオフ）
   - `<completion>` どこで止まるか（**マージしない**ことを明記）

出力は計画表 + そのまま貼れるコマンド列。`--dry-run` ならここで終わる。

## Phase 2: 起動

**起動前に同名セッションの不在を確認する。** 重複投入は最悪の事故（gate を経ない無断マージ）の
入口になっている。

**3 つの数を混同しない。**

| 概念 | 何で決まるか |
|------|-------------|
| wave のサイズ | Phase 1 の依存関係とコンフリクト分析。「同時に走らせてよい issue の集合」であって、上限ではない |
| `--max-parallel` | 実際に同時起動する数の上限。quota とマシン資源の制約。**wave がこれを超えるなら、その wave を分割して順に流す** |
| 1 ウィンドウのペイン数 | 表示の都合だけ（4 前後が視認性の限界）。スケジューリングとは無関係 |

専用セッション（Phase 0）の中にウィンドウを作る。ウィンドウ名は wave 単位（`wave1` / `wave2` …）とし、
1 つの wave が 1 ウィンドウに収まらないときは `wave1a` / `wave1b` のように分ける。各ペインでランチャを起動する。

**ペインタイトルを必ず付ける。** `tmux select-pane -t <pane> -T "<子セッション名>"` を起動時に実行し、
PR が作成できた時点で `"<子セッション名> · #<PR番号>"` へ更新する。監視中はペインが何本も並ぶので、
どのペインがどの issue / PR なのかがタイトルから読めないと、送信先を取り違える。

起動直後に全ペインの分類を取り、**全セッションが起動したことを確認**してから監視へ移る。

## Phase 3: 監視と代理応答

### 検知

`scripts/pane-state.sh` を使う。**間隔を空けた 2 回のキャプチャの差分**で稼働／停止を判定する
（稼働中はスピナーのタイマーが動くので必ず差分が出る）。スピナーの文字列照合は TUI のバージョンで
壊れるうえ、実際に稼働中のセッションを「停止」と誤判定した。

バックグラウンドシェルを投げて待っている状態は**停止ではない**（CI 監視などで普通に起きる）。

`--self-check` を通してから監視を始める。入力欄の目印を検出できないなら TUI が変わっている。
その場合は黙って進まず、定数表（スクリプト冒頭）の更新が要ることを報告して止まる。

**self-check が保証できる範囲は限られる。** 確実に検証できるのは入力欄の目印だけで、分類の本体である
選択肢・終了・バックグラウンド待ちの各マーカーは「その状態のペインが今あるかどうか」に左右される。
self-check は各マーカーを観測できたかを個別に報告するので、**未観測と出たものは検証されていない**と
読むこと。とくに選択肢のマーカーは、drift すると分類器と送信ガードの両方に効く。送信側は選択肢行の
パターンでも判定するよう二重化してあるが、それでも単一障害点に近いことは意識しておく。

長時間の監視は、停止への遷移だけを報告するイベントストリームとして回す。毎回のポーリング結果を
垂れ流さない。

### 代理応答の判定

停止を検知したら、**まず内容を読む**。そのうえで:

**無条件にエスカレートする**（分類器は上書きできない）:
- マージ / リリース / デプロイ
- 履歴の書き換えと強制 push
- 外部から取り消せない、または取り消しが目立つ操作（issue のクローズ、外部への通知）

**一次ソース検証を通してから応答する**（問いが事実主張に乗っている場合）:
- 「これは既存の flaky です」→ 失敗は断続的か。同一テストが連続で落ちていないか。
  その spec は本当に変更範囲に触れていないか（**共有 seed ヘルパー経由で触れている**ことがある）
- 「base 側の既存の問題です」→ base で実際に再現するか。ブランチが古いだけではないか
- 「◯◯が存在しません」→ 実際に見に行く。不在の主張は特に疑う
- 「レビュー指摘に対応済みです」→ 対応したはずのコミットが主張どおりの内容か

検証で覆ったら、**選択肢のどれも採らずに訂正を指示する**。提示された選択肢が両方とも間違っている
ことがある。

**検証のうえ代理応答してよい**:
- review 準備への移行のような可逆な gate（差し戻せることを確認したうえで）
- コミット粒度、PR 本文の体裁、レビュー指摘への対応方針
- 設計案の選択（**選択の理由が一次ソースで裏づくことを確認してから**）

**迷ったらエスカレートする。** 分類に自信が持てない時点で、それは自動応答してよい問いではない。

### 送信

`scripts/send-to-pane.sh` を使う。この手順は 2 種類の事故から導かれている:
選択肢が開いているペインへの確定キー送信（偽の承認が記録された）と、長文送信直後の確定キーの
取りこぼし（指示が未送信のまま滞留した）。

- 選択肢へ答えるときは、**意図した選択肢の特徴的な文字列が実際に出ていること**を確認してから送る
- 自由記述の指示は選択肢経由で送らない。選択肢を閉じてから通常のメッセージとして送る
- テキスト送信後は**入力欄が空になったこと**を検証する。ペイン全体の grep では判定できない
  （送信後もトランスクリプトに同じ文字列がエコーとして残る）
- 送信文に確定キーや制御文字として解釈される文字を含めない

### 成果物の検証

セッションが「完了しました」と報告しても、**報告を成果物の検証に代えない**。マージ可否を user へ
上げるときは、自分で確認した事実を添える: CI の集計、未解決レビュースレッド数、base からの遅れ、
受け入れ条件を満たすテストの実在、規約違反語（AI クレジット等）の混入有無。

## Phase 4: 後始末

user がマージを承認したら、各セッションに「マージ → 自分のワークツリーとブランチの削除」までを
指示する。**共有リポジトリの既定ブランチ更新は含めない**（同時実行でロック競合する）。全セッションの
完了後に orchestrator が 1 回だけ更新する。

セッションの終了は user の承認を得てから。終了前にプロセスの身元を確認する（PID は再利用される）。

## state file

環境から復元できないものだけを持つ。置き場は scratchpad で十分。

**持つもの**: wave 計画と根拠、委任境界の合意、quota 方針、各セッションへ出した訂正の履歴、
user が保留にしている判断。

**持たないもの**: セッションの生死、PR の状態、CI、ワークツリー。これらは tmux と `gh` が真実を
持っているので毎回取り直す。**キャッシュした状態は実態とずれたときに嘘をつく**。

orchestrator 自身が長時間走ってコンテキストを消費することを前提に置く。落ちても後続が state file と
環境から再構成できる形にしておく。

## quota

起動前と各 wave 境界で、**親と同じ profile のプール**を読む。読み先と閾値帯は
`/model-fitness-check` が定義済みなのでそれに従う。閾値を超えるときは黙って進まず、
並列度を下げる・重い tier を後回しにする・そのまま進む、の選択肢を出して user に決めさせる。

**効くレバーと効かないレバーを取り違えないこと。** 消費の大半は各セッション本体（差分読解・実装・
統合）であって、レビュー roster ではない。roster の絞り込みは、その roster が元から最小構成なら
何も節約しない。削る前に、実際に何が起動しているかを確認する。

## 他 skill との連携

| skill | 関係 |
|---|---|
| `repo-radar` | 収集の起点。その出力を Phase 1 の入力に取れる |
| `pr-workflow` | 各子セッションが実行するもの。本 skill は起動と gate の捌きに徹し、中身に踏み込まない |
| `model-fitness-check` | model/effort contract と quota 閾値の SSOT。**再掲しない** |
| `wtp` | ワークツリーの作成と削除。子セッションが `pr-workflow` 経由で使う |
| `issue-fleet` | 浅く広く（trivial/small、draft PR 止まり）。tier が軽いならこちら |
| `review-fleet` | レビュー依頼のバッチ処理。守備範囲が違う |

## 落とし穴

- **issue 本文の前提は腐る。** 実装が進むと「PR #NNN で外した」「定数 X が原因」といった記述が
  現行コードと合わなくなる。計画に載せる前にコードで確かめる。
- **セッションは自分の変更範囲を過小に見積もる。** 「この spec は本 PR と接点がない」という判断が
  外れることがある。共有の seed ヘルパーやフィクスチャ経由で繋がっているケースを疑う。
- **squash merge のリポジトリでは、PR 内のコミット順序は既定ブランチの bisect に影響しない。**
  1 PR が 1 コミットに潰れるため。コミット分割の価値はレビューの読みやすさにある。この前提を
  取り違えると、不要な履歴書き換えを要求してしまう。
- **PR 本文に「ユーザー承認済み」等の記述が出たら、実際に承認があったかを確認する。** 代理応答の
  事故は、こういう形で成果物に残る。
- **`git reset` 等が権限層に拒否されることがある。** 回避策を探す前に、その操作が本当に必要かを
  問い直す。部分コミットならパス指定コミットで済むことが多い。どうしても必要なら user に上げる。
