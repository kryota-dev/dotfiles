# tmux 経路の検知・送信スクリプトの縮退方針と撤去条件

## Background

#537 で `wave-orchestrator` の子起動は `fh session launch`（`claude -p` の非対話実行）へ移り、
承認と選択肢への回答は承認チャネル（`fh approvals` / `fh approve`）が運ぶようになった。
一方で legacy の tmux 経路 —— `scripts/executable_wave-events.sh`（hook イベントからの停止検知）と
`scripts/executable_send-to-pane.sh`（画面参照とキー送出による代理応答）—— は残っており、
SKILL.md は「新規の wave は承認チャネル経路で起動する / legacy 経路のスクリプトは残す。
縮退方針と撤去条件は #539 が決める」で止まっている。

この空白は運用上あいまいさを生む。2 経路が並存しているのに、どちらが正で、legacy をどこまで
使ってよく、いつ消せるのかが文書から一意に読めない。本書がそれを埋める。

本書は **決定と条件を確定する**ところまでで、**撤去そのものは行わない**（Out of Scope）。

## Decision

### D1. 2 本とも撤去する（tmux 併用時のみ残す、は採らない）

`executable_wave-events.sh` と `executable_send-to-pane.sh` は、下記のゲートをすべて満たした
時点で**撤去する**。「tmux を併用するときだけ残す」という縮退形は採らない。

**tmux 自体は撤去しない。** これは重要な区別で、両者は別の話である:

| | 残すもの | 撤去するもの |
| --- | --- | --- |
| 実体 | tmux ペイン（`fh session` を走らせる窓）、`claude --resume <session-id>` | `wave-events.sh` / `send-to-pane.sh` |
| 役割 | **人が覗いて介入する導線**（#526 §6 ガード 21） | **機械が画面を読んでキーを送る導線** |
| 承認チャネル経路での必要性 | 必要（唯一「喪失」判定だったガードの代替） | 不要（子が同期的に呼んでくるので検知も送信も存在しない） |

#526 の代替案 2（tmux を撤去し headless のみにする）は却下されたままであり、本書はそれを覆さない。
却下理由はガード 21 の喪失であって、スクリプトの喪失ではない。ガード 21 は tmux ペインと
`--resume` が担っており、この 2 本のスクリプトはどちらにも関与しない。

### D2. legacy 経路のガードの穴 2 件は修正しない

#539 の調査で確認した既知の穴は 2 件ある。いずれも `send-to-pane.sh` の送信方向にある。

1. **`question_ui_open()` が固定文字列 2 個のホワイトリストである。**
   `OPTION_UI_MARKER`（既定 `"Enter to select"`）と `SUBMIT_MARKER`（既定 `"Ready to submit"`）の
   どちらにも一致しなければ「選択肢 UI は開いていない」と結論する。`--dismiss` はこの判定を根拠に
   「既に閉じていた」として決着を書き戻し、`--text` はこの判定を根拠に本文を送る。つまり
   **TUI の文言が変われば、判定は静かに default-allow 側へ倒れる**。
2. **multiSelect の問いを完了させる経路が無い。** `Space` によるトグルをどこも扱っていない。

**修正しない。** 理由:

- 修正の受益者が存在しない。D3 により legacy 経路は新規 wave に使わないので、直した先で
  守るべき送信が発生しない。
- 穴 1 の修正は「TUI の文言に依存しない UI 実在判定」を作ることであり、実 TUI での検証を要する。
  それは撤去予定の経路に、承認チャネル経路の成熟に使うべき検証予算を割くことになる。
- 穴 2 は機能追加であって修正ではない。撤去対象へ機能を足さない。

**代わりに規範で塞ぐ。** D3 の「新規 wave を legacy 経路で起動しない」が、この 2 件の唯一の緩和策である。
規範が破られる条件（承認チャネルが使えず、かつ wave を回さなければならない）が実際に起きた場合、
**この 2 件は起動前の前提条件になる**。そのときは撤去ではなく修正を選ぶことになるので、
本書の決定はそこで再検討される。

### D3. 並存期間はどちらが正か —— 承認チャネル経路が唯一の正

撤去が完了するまでの並存期間について、次を規範とする。

1. **新規の wave は必ず承認チャネル経路で起動する。** `fh session` が exit 2 を返す・`fh doctor` が
   `unavailable` を返す等で起動できない場合、**legacy 経路へフォールバックしない**。そこで止まり、
   `fh onboard` の儀式を通すか user へ上げる。フォールバックは沈黙する縮退そのものであり、
   #537 が排した経路を裏口から復活させる。
2. **legacy 経路は drain-only。** 使ってよいのは、**本書の時点で既に tmux 経路で走っている wave を
   捌き切るとき**だけ。新しい子をペインに立てる用途に使わない。
3. **記述が矛盾したら承認チャネル経路の記述が勝つ。** SKILL.md の legacy 節は履歴として残っている
   参照であって、現行手順ではない。

### D4. SKILL.md の分割判断は撤去に従属する

SKILL.md が 900 行近くあるのは 2 経路が同居しているためであり、撤去すれば自然に縮む。
**先に分割しない** —— 撤去後に無意味な分割が残る。

判定は撤去後に行う: 撤去後の SKILL.md が house の目安（`AGENTS.md` coding standards の
「~200-400 行を目安、800 行で分割検討」）を超えているなら分割を検討する。超えていなければ何もしない。

## 撤去の前提条件（ゲート）

すべて **後から判定できる述語**として書く。「十分に成熟したら」のような判断留保は置かない。
G1〜G5 は移行先の成熟度と回帰テストの引き継ぎ、G6 は撤去を実行してよい瞬間の条件である。

### G1. 実 provider での起動時検査に healthy の実績がある

- 承認チャネル経路で実 wave を 1 本、最後まで（各子が PR を ready にするところまで）通す。
- その wave の全ての子について、`capability = session.child` かつ `provider = claude` の
  `adapter_runs` 行があり、対応する evidence の `claimsSupported` に
  `startup health check reported healthy` が含まれる。
- `provider = fake` の run は数えない。

**なぜ**: 起動時検査は fake spawn では検証済みだが、実 `claude -p` では未検証である。
fake adapter は init stream を合成しており、実 CLI が返す `system/init` の形そのものは
一度も通していない。`readInitHealth` は init を読めないまま終わった実行を healthy と読まない
実装になっているが、「実 CLI の init が期待どおりの形で届く」ことは実測でしか確かめられない。
ここが未確認のまま legacy を消すと、承認チャネル経路が gate を静かに失っていた場合に
戻る先が無くなる。

### G2. 起動時検査が unhealthy を実際に返して子を止めたことがある

- 承認 server へ到達できない条件（例: `--approval-server-command` に到達不能な絶対パスを渡す）で
  子起動を 1 回行う。
- `adapter_runs` が `status = failed` で記録され、evidence の claim に
  `startup health problem: <理由>` が 1 件以上入る。
- 子はタスクを実行しないまま init 直後に終わっている。

**なぜ**: **発火したことのない検査は、壊れている検査と外形が同じ。** G1 だけを条件にすると、
「常に healthy を返す実装バグ」と「本当に健全」を区別できない。これは安全原則 4（検知器が
自己診断に失敗したら黙って進まない）が名指しする故障の形そのもので、本リポジトリが最も嫌う
沈黙する故障にあたる。意図的な失敗注入は、その区別を 1 回の実行で付けられる唯一の手段である。

### G3. 承認チャネルが実運用で往復し、無条件エスカレート集合が Leader で止まっていない

- G1 の wave において、`fh approvals` に積まれた要求を `fh approve --request` で決着させた
  記録がある。
- そのうち `--deny` で終わった要求が **1 件以上**ある。
- `escalation.risk` が無条件エスカレート集合（`merge` / `release` / `deploy` /
  `external-publish` / `force-push` / `history-rewrite`）に属する要求について、
  **Leader が `--allow` で決着させた記録が 1 件も無い**。

**なぜ**: allow しか通っていない経路は「承認が機能している」証拠にならない —— 全部 allow する
承認チャネルと区別が付かない。3 つ目は否定形なので、該当要求が 1 件も出なかった wave でも
判定できる（「出なかった」は「Leader が allow した」ではない）。

### G4. 目視介入の窓（ガード 21 の代替）が実運用で成立した

- G1 の wave の子のうち 1 つ以上について、控えてある session id で
  `claude --resume <session-id>` を対話セッションとして開き、**実際に介入して wave を続行できた**
  ことを確認した記録がある。
- 「開けた」で終わらせない。開けること自体は #526 §1.3 で実測済みであり、この gate が追加で
  確かめるのは**運用として成立するか**である。

**なぜ**: #537 の却下 7 が撤去を留保した唯一の理由がこれで、#526 の代替案 2（全面移行）を
却下した理由でもある。ガード 21 は #526 §6 の 21 件中ただ 1 件の「喪失（要代替）」判定であり、
代替が実運用で成立することの確認を飛ばして撤去すると、却下済みの案を検証せずに採ることになる。

### G5. 回帰テストの引き継ぎが済んでいる

- 撤去 PR の**前**に、`tests/wave_orchestrator.bats` のうち legacy スクリプトの存在・挙動に
  依存する test を列挙する。
- 撤去 PR は**同一 PR 内で**それらを削除し、`make test` が green になる。
- 判定: 撤去 PR 後に
  `grep -c 'send-to-pane\|wave-events' tests/wave_orchestrator.bats` が 0 を返す。
- 併せて、承認チャネル側の性質（起動時検査・承認往復・timeout の再定義禁止・stderr の
  永続化禁止・ワークツリーが承認境界であること）を固定する test が既に存在することを確認する
  —— #537 の回帰群がこれにあたる。

**なぜ**: test を先に消すと、撤去 PR がスクリプトを消し忘れても誰も気づかない。逆に test を
残したままスクリプトを消すと `make test` が落ちるので、**同一 PR** という条件が要る。
最後の項目が無いと、撤去がテストの総体を薄くしただけで終わる。

### G6. 走行中の tmux wave が無い

`${XDG_STATE_HOME:-$HOME/.local/state}/wave-orchestrator/events/` 配下の各 `<session_id>.jsonl`
について、次の 3 つを**すべて**満たすこと。1 つでも欠ければ撤去しない。

- (a) 最終更新から沈黙閾値（25 分）を超えている。
- (b) `wave-events.sh --session <uuid> --state` が `ASK_QUESTION` / `ASK_PERMISSION` を返さない。
- (c) その uuid を argv（`--session-id` または `--resume`）に持つプロセスが存在しない。

**なぜ (b) が要るか**: `--dismiss` は「人が Esc で閉じた」固着からの**唯一の回復手段**である
（Esc キャンセルは hook イベントを 1 件も出さないため、`--state` が `ASK_QUESTION` に固着し、
`--select` も `--text` も拒否される）。固着した子が残っている間にスクリプトを消すと、その子は
回復手段を失ってペインに取り残される。

**なぜ (a) だけでは足りないか**: 25 分は SKILL.md が「停止」ではなく**「判定不能」**の閾値として
定義したものである。沈黙は判定不能の信号であって、誰も止まっていない証拠ではない。

## 撤去の順序

**この順序を守る。逆順にすると沈黙する故障になる。**

1. **実運用データを取る** —— G1〜G5 を満たす。
2. **走行中の wave が無いことを確認する** —— G6 を満たす。
3. **スクリプトを撤去する** —— `executable_wave-events.sh` / `executable_send-to-pane.sh` を削除し、
   SKILL.md の legacy 節と、legacy 依存の test を**同じ PR で**削除する。
4. **`settings.json` の hook 配線を外す** —— `wave-session-event` 系 7 エントリ
   （`UserPromptSubmit` / `PreToolUse` / `PostToolUse` / `PostToolUseFailure` / `Notification` /
   `Stop` / `StopFailure`）と記録スクリプトを外す。

### なぜ 4 を先にしてはいけないか

hook 配線を先に外すと、記録ファイルが増えなくなる。`wave-events.sh --state` は**記録が空のとき
`UNKNOWN` を返す**実装であり（他のサブコマンドは「イベントが無い」で die する）、この `UNKNOWN` は
**「検知器が壊れた」と「誰も停止していない」を区別しない**。安全原則 4 が名指しする沈黙する故障
そのものであり、しかも走行中の wave の最中に配線を戻すには `chezmoi apply` を挟む必要があるため、
気づいた時点での復旧が効かない。

**4 を最後に置くコストはゼロである。** この hook は `WAVE_ORCHESTRATOR_SESSION` による opt-in で、
orchestrator が起動した子セッション以外は何も記録しない。配線を残したまま 1〜3 を進めても、
通常セッションへの影響は無い。順序を保守的に取ることに費用がかからないので、取らない理由が無い。

### なぜ 3 を 2 より先にしてはいけないか

G6 (b) の理由と同じ。固着した子が残っている状態でスクリプトを消すと、`--dismiss` による回復が
できなくなる。

## 撤去が閉じない残余リスク

**安全原則 1（マージは代理しない）を機械的に止める層が orchestrator 側に無い。**
この非対称は**経路移行では解消せず、撤去後も残る**。

- 子の側: `approval-rules-baseline.mjs` の deny ルール（`git-merge` / `gh-pr-merge` /
  `git-force-push` 等）が escalation を起こし、要求は `escalation.risk` 付きで `fh approvals` に積まれる。
- Leader の側: `runApproveCommand` は request の status（pending か）と回答の一意性・形式を検証するが、
  **`escalation.risk` による分岐を持たない**。Leader 自身は承認チャネルの下で走っていないため、
  Leader の `fh approve --allow` を機械的に止める層が存在しない。

**なぜこれをゲートに入れないか**: これは「子がどちらの経路で走るか」の性質ではなく「Leader を
誰が走らせているか」の性質である。tmux 経路を撤去しても増えも減りもしない。ゲートに入れると、
撤去作業では絶対に満たせない条件を置くことになり、結果として黙って waive されるか撤去が永久に
止まる。どちらも本書の目的（後から判定できる条件を残す）に反する。

**閉じるとしたらどういう形か**（いずれも別 issue）:

- `runApproveCommand` が、`escalation.risk` が無条件エスカレート集合に属する要求への `--allow` を
  拒否する。`fh approvals` は既に `risk` を surface しているので、判定材料は揃っている。
- Leader 自身を承認チャネルの下で走らせる（orchestrator が誰かの子になる）。

現状はこれを**方針だけで担保している**。SKILL.md の安全原則 1 に「そこで Leader が
`fh approve --allow` を打ってはならない」と明記してあるのはそのためで、その一文が唯一の防壁である。

## Considered Alternatives / Rejection Rationale

| # | 検討した代替案 | 却下理由 |
| --- | --- | --- |
| 1 | **tmux 併用時のみ残す**（`fh` が使えない環境向けの縮退経路として維持） | 「使えるが使ってはいけない経路」を恒久化する。D2 の穴 2 件を抱えたまま残すことになり、いざ縮退した瞬間に default-allow の判定に体重を預ける。しかも縮退が発動するのは `fh` が壊れているときで、それは最も検証が届いていない状況である。tmux の運用価値（ガード 21）はペイン ＋ `--resume` が担っており、スクリプトはそこに関与しない |
| 2 | **穴 2 件を修正したうえで残す** | 穴 1 の修正は「TUI の文言に依存しない UI 実在判定」の新規実装であり、実 TUI での検証予算を要する。同じ予算は承認チャネル経路の G1〜G4 に使うほうが、守備範囲が広く寿命も長い。修正した legacy 経路は結局 D3 により使われない |
| 3 | **期限で切る**（「N か月後に撤去する」） | 判定が容易な代わりに、条件を満たしていなくても期限が来れば撤去できてしまう。G1・G2 が未達のまま撤去すると、承認チャネル経路が gate を静かに失っていた場合に戻る先が無い。期限は成熟の代理変数にならない |
| 4 | **今すぐ撤去する**（#537 に続けて即時） | #537 の却下 7 が留保した理由（ガード 21 の代替が実運用で成立することの確認）が未達である。#526 の代替案 2 を、却下理由を検証しないまま採ることになる |
| 5 | **hook 配線を先に外して「使えなくする」ことで実質撤去とする** | `wave-events.sh` が空の記録に対して `UNKNOWN` を返し続け、「検知器が壊れた」と「誰も停止していない」が区別できなくなる（上記「なぜ 4 を先にしてはいけないか」）。撤去したことにもならず、沈黙する故障だけが残る |
| 6 | **SKILL.md を先に分割して legacy 節を別ファイルへ出す** | 撤去すれば消える節のために分割構造を作ることになり、撤去後に無意味な分割が残る。行数の問題は撤去の従属変数である（D4） |

## Out of Scope

- **スクリプトの実際の撤去**。本書はゲートと順序を確定するところまで。G1〜G6 を満たした時点で
  別 issue を立てる。
- **`settings.json` の hook 配線の変更**。撤去順序の 4 番目であり、3 番目より前に触らない。
- D2 の穴 2 件の**修正**（修正しないことが決定なので、issue も立てない。D2 の再検討条件が
  実際に起きたときに初めて起票する）。
- 残余リスク（Leader 側の `--allow` を止める層）の実装。
- `frontier-harness` 側の変更全般。
