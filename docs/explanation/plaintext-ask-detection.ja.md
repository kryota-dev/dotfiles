# 平文で判断を仰いだまま終わる turn を検知する

🌐 English (canonical): [plaintext-ask-detection.md](plaintext-ask-detection.md)

← [ドキュメント目次](../README.ja.md)

配布しているエージェント指示は、判断を仰ぐときは `AskUserQuestion` を使い、応答末尾の平文で
問いかけて待たないことを要求している。しかし指示だけでは守られなかった。1 セッション中に同じ
違反が 3 度起き、うち 2 度はユーザーの明示的な指摘の後、1 度は規約自体をマージ・配布した後で
ある。[`#616`][issue] はまず**そもそも機械的に検知できるのか**という手前の問いを立て、
「できるはずを前提に設計しない」ことを明示的に求めた。

このドキュメントは、何を実測したか、どう再現するか、そして出来上がった hook が何をして
何を意図的にしないかを記録する。

## 結論: 検知できる。根拠は以下

`Stop` hook のペイロードは応答本文を運び、かつ同じ turn をトランスクリプト上で特定できるだけの
識別子を運ぶ。両方が要る —— 本文だけでは「ちゃんと選択肢を出してから要約した」正常系と違反を
区別できないからである。

### 実機で採取したペイロード

Claude Code は自身のデバッグログに hook のペイロードを書き出す。以下は
`~/.claude/debug/<session>.txt` から回収した実物（セッション ID は伏字、パスは短縮）:

```json
{
  "session_id": "[REDACTED]",
  "transcript_path": "/Users/<user>/.claude/projects/-private-tmp/<session>.jsonl",
  "cwd": "/private/tmp",
  "prompt_id": "835ed30b-6fea-4886-b00e-917807befe28",
  "permission_mode": "auto",
  "effort": { "level": "xhigh" },
  "hook_event_name": "Stop",
  "stop_hook_active": false,
  "last_assistant_message": "了解しました。何かお手伝いできることがあれば教えてください。",
  "background_tasks": [],
  "session_crons": []
}
```

新しく採り直すには、任意のセッションを `claude --debug-file <path>` で起動し、そのファイルを
`stop_hook_active` で grep する。stdin をファイルへ書き出すだけの `Stop` hook でも採れるが、
その場合は CLI が受け付ける設定ファイルが要るので、sandbox 環境では塞がれることがある。

### 各フィールドの役割

権威はこの表ではなくランタイム自身の schema 記述にある:

| フィールド | 検知器が使う理由 |
|---|---|
| `last_assistant_message` | 応答本文。ランタイム側が「hook がトランスクリプトを読んで parse せずに済むように」存在すると説明しているフィールド。省略可（tool 呼び出しだけで終わった turn には無い）。 |
| `transcript_path` | セッションの JSONL トランスクリプトへのパス。こちらには全 tool 呼び出しが残る。 |
| `prompt_id` | 「1 つのユーザープロンプトと、次のプロンプトまでの全イベントを対応づける UUID」。「**この** turn の中で」を表現できるのはこれのおかげ。 |
| `background_tasks` | 「session is done」と「バックグラウンド待ちで止まっている」を hook が区別できるようにするもの、とランタイムが説明している。何も走っていなければ空配列。 |
| `stop_hook_active` | 既に hook がこの turn の終了をブロックしたときに true。多重発火の抑止に使う。 |
| `agent_id` | サブエージェントの内側から発火したときだけ存在する。 |

### トランスクリプト側は実データで検証した

合成 fixture ではなく、このリポジトリのセッションが実際に生成したトランスクリプトに対して
次の 2 点を確認した:

1. ペイロードの `prompt_id` は、その turn を開始した `user` エントリの `promptId` と一致する。
   assistant エントリは `promptId: null` を持ち、turn の途中で返る `tool_result` エントリは
   開始プロンプトと同じ `promptId` を持つ。よって「この ID を持つ最初の行以降すべて」が
   turn の窓として妥当である。
2. `AskUserQuestion` は `assistant` エントリ上の通常の `tool_use` ブロックとして現れ、
   メインエージェントでは `isSidechain: false` である。

したがって検知器の第 2 段は「turn の開始エントリから走査し、次のプロンプトで打ち切り、その間に
`AskUserQuestion` の呼び出しがあったか」を見るだけでよい。窓を次のプロンプトで閉じることが、
**後続の行儀のよい turn が過去の違反を打ち消してしまう**のを防いでいる。

## `Stop` はターンの終わりを意味しない

設計が乗り越えねばならない罠がここにある。サブエージェントへ委任した親は途中で `Stop` を出し、
**同じ `prompt_id` のまま**再開する —— この実測は `wave-orchestrator` skill が持っており、
「1 ターンに `Stop` は最後の 1 回だけ」と仮定した過去の設計は、実際に止まっている子を
取り違えて報告していた。

これを解くのが `background_tasks` であり、この機能が**いま**検知可能になった理由でもある。
配列が空でなければ、セッションは終わったのではなくバックグラウンド待ちで止まっている。
検知器はそのペイロードを丸ごとスキップする。

このガードは網羅性の証明ではない。語句の段が二重の守りになっている —— 委任途中の `Stop` の
本文は「レビュアーを起動しました」の類であり、語句リストのどれにも当たらない。

## hook がしていること

[`home/dot_claude/executable_plaintext-ask-check.sh`](../../home/dot_claude/executable_plaintext-ask-check.sh)
を `stop:plaintext-ask-check` として配線している。

**第 1 段 —— 安価で、毎 turn 走る。** `last_assistant_message` の末尾の窓
（`TAIL_SCAN_CHARS`、400 文字）を取り、そこから**締めの 1 行**を求め、その行を明示列挙した
「判断を仰ぐ語句」と照合する。ここはすべて bash の文字列照合で、通常の turn で起動する外部
プロセスは全体で 4 個である。

締めの行は、末尾から空行・箇条書き・引用・見出しの行を捨てて求める。観測された違反の形は
問いの**下に**選択肢を並べることが多く、実際の最終行はしばしば `- B: ...` になるからである。

**窓の単位はバイトではなく文字である。** バイトで切ると多バイト文字の途中で切れることがあり、
そうなると BSD/ugrep の `grep -F` は**その後ろにある完全な日本語語句すら一致しなくなる**
（実測。`LC_ALL=C` でも同じ）。窓より長い応答はごく普通に起きるので、バイト窓は
**この検知器が守るべきまさにその turn で、黙って落ちる**経路だった。bash の部分文字列展開は
UTF-8 ロケールで文字単位に働くので境界を割らない。ただし `${var: -N}` は N が文字列長を
超えるとクランプせず**空文字列を返す**（bash 3.2 で実測）ので、展開の前に長さで抑える必要が
ある —— 抑えなければ、これもまた沈黙してゼロ件に見える経路になる。

**第 2 段 —— 第 1 段が当たったときだけ。** トランスクリプトを読み、この turn で
`AskUserQuestion` が呼ばれたかを判定する。第 1 段はめったに当たらないので、通常の turn が
トランスクリプト走査のコストを払うことはない。非一致のケースに読めないトランスクリプトのパスを
渡すテストが、この契約を固定している。

### 語句リストは意図的に狭く、位置も判定条件に含める

許容する誤りの向きは「止めない側」である。違反の見逃しは許容するが、通常の報告への警告は
許容しない —— うるさい検知器は切られ、切られた検知器は何も守らないからである。よってリストは
具体的な判断要求の結びだけを列挙し、一般的な疑問形や、報告が普通に使う結びは除外している。

窓の中のどこかに語句があれば当てる、では足りない。それでは、かつて尋ねた問いを引用した完了報告が
違反になってしまう。検知器は応答が判断要求で**終わっている**ことを要求する。日本語の語句は
文末に来るので「文末句読点を剥がした締めの行がその語句で終わること」を、英語の語句は文頭寄りに
来るので「締めの行が `?` で終わること」を条件にする。この 1 つの規則が
`Let me know if you want me to proceed?` と `Done. Let me know if you spot anything else.` を
分けている。

リストはスクリプト内の名前付き定数で、誤検知しないことは `tests/claude_hooks.bats` が固定する。

### 三値出力 —— 壊れた検知器が「異常なし」に見えないように

検知器の沈黙する故障は「違反 0 件」と見分けがつかない。これはこのリポジトリが最も嫌う故障の
形である。そこで hook は必ず 1 行の機械可読な status を stderr に書く:

| status | stdout | 意味 |
|---|---|---|
| `ok` | — | 評価した。違反なし。 |
| `skipped` | — | 評価対象外（turn 途中の `Stop`、サブエージェント、再入、本文なし）。 |
| `violation` | `{"systemMessage": …}` | 検知した。 |
| `error` | 第 1 段が既に当たっていれば `{"systemMessage": …}` | **評価できなかった**（jq 不在、走査窓の設定が壊れている、payload が parse できない、`transcript_path` が読める `.jsonl` でない、サイズ上限超過、解釈できない行、`prompt_id` がトランスクリプトに無い）。 |

`ok` と `error` は別の値であり、別のままであること、および各 error 経路がそれぞれの理由を
報告することをテストが固定している。兄弟の `Stop` hook が jq 不在を silent no-op として扱うのに
対し、この hook は `error` を返す —— 検知器にとって「評価できない」は「何も見つからなかった」
ではないからである。

走査窓を検証しているのも同じ理由による。窓をゼロにすれば何も一致しなくなり、きれいな `ok` に
見える —— 痕跡を残さずにこの検知器を無効化できる唯一の道になってしまう。他の失敗経路がすべて
`error` を返すのだから、ここも返す。

トランスクリプトの走査は `jq` の 1 パスで 3 つの真偽値に畳む。ファイルがどれだけ大きくても、
どれだけ壊れていても、走査中に保持するメモリは一定である。実トランスクリプトを連結した実測で
スループットは約 120 MB/s（417 MB を 3.4 秒）。64 MiB の上限はおよそ 0.55 秒に相当し、hook の
timeout 5 秒に対して約 9 倍の余裕がある。

exit code は常に 0。これは gate ではなく警告なので、`decision` / `continue` / `stopReason` を
一切出力せず、そのこともテストで固定している。

### 他の `Stop` hook が非同期なのに、これだけ同期な理由

`async` hook の stdout は後から回収され、モデル向けの attachment として配送される。ここで
出したいのは turn が終わったその時点でユーザーに見えるメッセージなので、エントリでは `async` を
省き、代わりに短いタイムアウトを置く。同期エントリはリポジトリに既に前例があり、新しい形では
ない。

## 限界

- **語句ベースなので、リストの範囲に縛られる。** 誰も列挙していない言い回しで判断を求められたら
  見逃す。これは選んだ誤りの向きであって、見落としではない。
- **turn の未来は見えない。** バックグラウンド作業が登録されていない状態で `Stop` が turn 途中に
  来て、その後にエージェントが `AskUserQuestion` を呼ぶつもりだった場合、警告は空振りになる。
  代償は 1 行のテキストだけで、何もブロックしない。
- **ペイロードの契約は公開 API ではない。** 将来のリリースが `last_assistant_message` を落とす
  か `prompt_id` を改名したら、hook は黙って通すのではなく `error` を報告する —— 上の採取手順で
  検証し直すこと。
